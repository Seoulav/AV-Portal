# W-20261004-021 — 잠긴 PDF 내려받기 검증 기록

## 판정과 변경

2026-10-05 `origin/main` `8efc8f1717218f9d42d83c365e212d58c00fe014`에서 시작했다. 세 파일은 이미 암호화되어 있었고 PDF.js는 비밀번호 없이 페이지를 열지 못했다. 문제는 상세 카드의 직접 내려받기 링크와, 뷰어가 비밀번호 확인 전에 내려받기 링크를 활성화하던 순서였다. 암호나 PDF 바이트는 변경하지 않았다.

| 파일 | 업로드 연결 | SHA-256 (변경 전후 동일) |
|---|---:|---|
| `samsung-115qhf-spec-ko.pdf` | 1 | `b1773b9b39ccbabe5d3dffc408b09f219c775ea762ae66777d6ad540b1a26b5f` |
| `samsung-lcd-signage-product-guide-ko.pdf` | 9 | `0a01151782576d87a4873e4968255884639b0656e1ccf1b794ab76f1d9249e72` |
| `samsung-videowall-product-guide-ko.pdf` | 2 | `da24b9fa9c1b42d531b09ff584d539c8487d3780885c0683b12c9a0cc5c11dda` |

`manifest.json` 업로드 103건 중 12건에만 `locked: true`를 붙였다. 잠긴 자료의 상세 카드 `↓ 내려받기`는 뷰어를 여는 버튼이 됐다. 뷰어는 열 때 내려받기 링크를 제거하고, PDF.js의 `task.promise`가 비밀번호 확인 후 성공한 경우에만 링크를 건다. 틀리면 다시 입력을 요청하고 링크를 잠근 채 둔다. 닫고 다시 열면 링크와 입력 상태가 초기화된다. 평문 자료의 상세 카드 직접 링크는 유지했다. 비밀번호는 코드·검사·문서에 기록하지 않았다.

## 검사와 RED → GREEN

`tests/document-lock.test.mjs` 6/6 통과. 실제 PDF.js로 암호 PDF가 비밀번호를 요구하고 잘못된 비밀번호에서 재시도를 요구함을 확인했다. 메타데이터 검사 네 경우는 다음과 같다.

| 목록 표시 | 실제 PDF | 결과 |
|---|---|---|
| `locked: true` | 암호화 | 통과 |
| 생략 | 평문 | 통과 |
| `locked: true` | 평문 | 실패 |
| 생략 | 암호화 | 실패 |

`beta/verify-pages.mjs`는 업로드 고유 PDF 56개를 PDF.js로 실제 열어 목록 표시와 대조한다. 공유 파일의 제품별 잠금 표시도 동일해야 한다. 실제 manifest를 임시로 바꿔 평문에 잠금을 표시하고, 암호 PDF의 표시를 뺀 두 경우 각각 `verify-pages` 종료 코드 1과 해당 파일명 오류를 확인한 뒤 `finally`에서 원상 복원했다. 전용 검사는 변경 전 표시 누락과 카드 직접 다운로드를 RED로 확인하고 변경 후 GREEN으로 확인했다.

독립 리뷰의 Important 지적은 버튼·팝업의 실제 흐름 검사가 임시 스크립트에만 있다는 것이었다. 이를 [재실행 가능한 Chromium 검사](../../tests/manual/document-lock-browser.mjs)로 저장했다. 로컬 환경변수 `W021_PDF_PASSWORD`에 사용자 제공 암호를 설정한 상태에서 저장소 루트에서 `node tests/manual/document-lock-browser.mjs`를 실행한다. 브라우저 자동 발견이 안 되면 `CHROMIUM_BIN`을 지정한다. 스크립트에 암호 값은 없다. 필수 변수는 서버·임시 폴더 생성 전에 확인한다. 재실행 결과 1280px·390px 모두 통과했고, 독립 재리뷰에서 남은 Critical/Important 0건이었다.

1280px·390px에서 잠긴 카드 버튼에는 직접 `href`가 없고, 뷰어는 입력 전·오입력 후 `href`가 없으며 원문 링크도 숨겨졌다. 정답 입력 후 PDF 렌더링과 다운로드 파일 생성을 확인했고, 닫고 다시 열면 다시 묻는다. 평문 한글 사용설명서 카드에는 즉시 내려받기 링크가 남아 있고 뷰어는 비밀번호 없이 열린다. 두 너비 모두 가로 넘침·페이지 JS 예외 0건이다. 캡처는 [화면 기록](W-20261004-021-screens/)의 `lh115qhfebgxkr-{1280,390}-{locked,wrong-password,unlocked,plain}.png` 여덟 장이다.

`node --test --test-concurrency=1 tests/*.test.mjs`: **319 tests / 318 pass / 0 fail / 1 기존 skip**. `node beta/verify-pages.mjs`: **249 장비 / 242 상세 / 382 WebP / 103 업로드 PDF**, 통과. 검색 인덱스 `--check`, 읽기 카탈로그 생성, `git diff --check` 통과. `npm.cmd test`는 두 번 재실행해도 기존 Windows RTCOM 테스트의 임시 디렉터리 `rename EPERM`으로 실패했다. 변경한 잠금 검사에서는 실패가 없었고, 동일 전체 검사를 직렬 실행하면 위 수치로 통과했다. CI의 `npm test` 결과는 PR에서 별도로 확인한다.

`git diff`에서 세 PDF·제품 JSON 242종·`mirrors` 변경 0건을 확인했다. 현재 저장소 변경분에서 사용자 제공 비밀번호 문자열 0건을 확인한다. 공개 Git 과거 원본 문제와 비밀번호 변경은 이번 범위 밖이다.

## 정적 사이트의 한계

잠긴 카드 버튼과 뷰어 내려받기 링크는 비밀번호 확인 전 막히지만 PDF 파일의 공개 주소는 그대로다. 로컬 정적 서버의 파일 직접 URL은 **HTTP 200**으로 다운로드됐다. 배포 후 공개 URL에서도 다시 확인한다. GitHub Pages에서 직접 URL 다운로드를 서버 측에서 막을 수는 없다. 실제 문서 열기 보호는 PDF 자체의 AES-256 암호화에 의존한다.
