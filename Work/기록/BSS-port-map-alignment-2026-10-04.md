# BSS 후면 Port Map 번호 블록 전수 점검 (2026-10-04)

사용자가 `blu-101` 공개 화면에서 번호 괄호가 실제 단자 블록과 어긋난다고 지적했다. 직접 승인한 수정 범위는 **BSS 5종의 기존 번호·라벨·설명을 유지한 채 후면 사진 좌표만 재측정**하는 것이다. 렌더러·스타일·사진·I/O는 바꾸지 않았다.

## 점검 결과

| 모델 | 기존 지도 번호 | 좌표 수정 | 판정 |
|---|---:|---:|---|
| `blu-100` | 11 | 5 | 아날로그 입력 A~C·출력 D~E의 색상 블록 경계에 맞춤 |
| `blu-101` | 11 | 5 | 사진의 녹색 입력 3블록·주황색 출력 2블록 경계에 맞춤 |
| `blu-160` | 10 | 4 | 상·하 옵션 I/O 카드 슬롯 A~D 외곽에 맞춤 |
| `blu-50v2` | 15 | 8 | 4입력·4출력 Phoenix 채널 경계에 맞춤 |
| `blu-dan` | 6 | 0 | Dante·BLU link·Ethernet·RS-232 번호가 이미 실물에 맞음 |

나머지 BSS 4종(`blu-aec-in`, `blucard-in`, `blucard-out`, `ec-4bv`)에는 Rear 사진·Port Map이 없으며 이번에 추정해서 만들지 않았다. **5종 53개 번호 중 22개 좌표만 변경**했다. 각 번호의 이전·수정 좌표와 이미지 SHA-256은 [근거 JSON](BSS-port-map-alignment-2026-10-04-evidence.json)에 있다.

## 측정과 화면

게시 Rear WebP를 원본 해상도로 디코딩했다. BLU-100·101의 Phoenix는 녹색 입력과 주황색 출력의 색상 경계를 재고, BLU-160은 상·하 카드 슬롯 외곽을 각각 재며, BLU-50v2는 4채널 색상 블록 안의 채널 경계를 나눠 확인했다. `blu-dan`은 사진과 기존 번호를 대조해 변경이 필요하지 않았다. 기존 라벨·설명·번호 순서와 `side`·`y`는 유지했다. 사진 5개의 SHA-256은 모두 변경 전과 같다.

[수정 전후 캡처 36장과 QA 결과](BSS-port-map-alignment-2026-10-04-screens/)는 5종 × 1280px·390px 기본 20화면에 더해 **좌표를 고친 4종의 390px 사진을 가운데·오른쪽으로 스크롤한 전후 16화면**을 담는다. 처음 캡처는 왼쪽만 보여 BLU-160·BLU-50v2의 수정 단자를 가렸고, 독립 리뷰 Important 지적에 따라 보완했다. 가운데·오른쪽 캡처의 전후 SHA-256은 8쌍 모두 다르며 수정 괄호가 해당 물리 블록을 가리킨다. 수정 후 기본 10화면은 번호 수와 설명 카드 수가 같고, 이미지 로드 성공, 번호 겹침·가로 페이지 넘침·JS 오류가 없다. 390px에서 긴 사진은 기존 가로 이동 안내에 따라 스크롤한다.

## 검증·범위

`tests/bss-port-map-alignment.test.mjs`는 실측 단자 경계와 이미지 SHA-256, 다섯 제품의 좌표 외 데이터 불변을 고정한다. 과거 작업의 전체 제품 고정값 검사는 이번 좌표만 역변환해 당시 스냅샷을 계속 확인한다. 제품별 변경은 JSON의 `portMap.items[].x1/x2`뿐이며, `sources`·사양·I/O·Signal Flow·제품 사진과 BSS 외 제품은 그대로다.

검증 결과: 전용 검사 **4/4**, 전체 `npm.cmd test` **316 중 315 pass / 0 fail / 기존 skip 1**. 처음에는 과거 배치의 “나머지 모든 JSON 불변” 검사 20개가 수정된 BSS 좌표를 감지해 실패했다. [역변환 도우미](../../tests/bss-alignment-history.mjs)를 각 역사 검사에 적용하되 **기존 근거 파일·고정 SHA는 그대로** 두어 재실행 통과했다. `verify-pages`는 **249·242·382 WebP·103 PDF**, 검색 인덱스 `--check`와 읽기 카탈로그 생성도 통과했다. 검색 인덱스의 `sourceSha256` 외 내용은 같고 공개 스냅샷에서 바뀐 제품 SHA는 좌표 수정 4종뿐이다.

커밋 뒤 병렬 `npm.cmd test` 재검에서 기존 Windows RTCOM 임시 폴더 `rename EPERM`이 두 번 재발했다. 직렬 `node --test --test-concurrency=1 tests/*.test.mjs`는 **316 / 315 pass / 0 fail / 1 skip**으로 통과했다. 좌표 검사 4건과 Pages·검색 인덱스·PR diff 검사도 별도로 통과했다.

독립 리뷰는 **Critical 0**, **Important 1**(모바일 첫 구간 캡처만으로는 수정 단자를 볼 수 없음)이었고 위의 스크롤 캡처로 처리했다. Minor 1건은 전용 검사의 경계 수치가 실측 독립성 자체를 증명하지는 않는다는 점이다. 경계의 측정 과정·원본 사진 해시를 이 기록과 근거 JSON에 남기고, 검사는 향후 좌표 드리프트를 막는 역할로 한정했다.

다른 제조사 Port Map 확대는 이 작업에 포함하지 않는다.

## 병합·공개 확인

[PR #280](https://github.com/Seoulav/AV-Portal/pull/280)은 `61e649d385fc4a324b43b79697354f0a09e5cccd`로 병합됐고 [Pages run 37212959724](https://github.com/Seoulav/AV-Portal/actions/runs/37212959724)이 성공했다. 공개 BSS 5종 JSON은 병합본과 바이트 단위로 같다. 실제 1280px·390px **10화면**의 마커·설명 카드 수는 11·11·10·15·6개로 일치하고, 이미지 로드, 가로 넘침·JS 오류 0이다. 모바일의 사진을 오른쪽까지 스크롤해 수정한 단자 위치를 공개 `blu-101` 화면에서 다시 확인했다. 최초 공개 검증 스크립트의 390px 설정이 실제 뷰포트에 적용되지 않은 문제를 발견해 명시 설정 후 재검한 결과만 위 수치로 기록했다.
