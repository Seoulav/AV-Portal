## 3. 명세에서 보완할 위험

### 1단계: 기존 화면 유지와 전역 스타일의 충돌

원문은 토큰·클래스만 준비하라고 하면서 body 배경·글자색·글꼴을 전역 적용한다. PROMPTS에는 기존 모습을 바꾸지 말라는 지시가 있고, 완료 조건에는 기존 본문도 Pretendard가 되어야 한다고 적혀 있다. 글꼴만 바꿔도 폭·줄바꿈이 달라질 수 있다.

권고: 1단계는 공통 CSS와 글꼴을 준비하되 **새 전역 스타일은 견본에만 적용**한다. 기존 홈·상세는 CSS 연결만 하고 시각 적용은 2·3단계로 미룬다. 이 경우 기존 본문의 실제 글꼴 변경 완료 조건도 2·3단계로 옮겨야 한다. 사용자 결정 전 임의로 한쪽을 선택하지 않는다.

기존 CSS도 Pretendard 이름을 이미 사용하므로 font-face 등록만으로 바뀌는지 확인해야 한다. 완전한 모습 유지가 선택되면 견본에서만 새 font-face를 활성화하는 방법까지 포함한다.

### 가독성·반응형·탐색

- 원문 10.5px 표 헤더·상태 배지는 모바일 최소 11px 규칙과 모순이다. 작은 글자는 최소 크기와 대비를 우선하는 보정 승인이 필요하다.
- 360px 왼쪽 열과 오른쪽 4열 단자 카드는 긴 명칭·조건에 좁다. 화면 폭뿐 아니라 실제 카드 폭에 맞춰 열 수를 줄이고 긴 명칭은 줄바꿈해야 한다.
- 1000px 이하는 1열인데 카드 순서는 720px 이하에서만 지정돼 있다. 721~1000px 순서도 정의해야 한다. CSS order만으로 시각 순서를 바꾸면 키보드/읽기 순서가 달라질 수 있어 DOM은 01→07 순서로 두는 방식을 권고한다.
- `#io`·`#documents`가 가리키는 카드가 없는 경우에도 이동 규칙이 필요하다. 원문은 관련 제품만 overview fallback을 정했다. 모든 숨김 대상에 일관된 fallback이 필요하다.
- 인쇄 시 닫힌 details를 CSS만으로 펼쳤다고 가정하지 않는다. 설명·전체 사양·전체 단자·기록을 포함하는지 실제 인쇄 미리보기 확인이 필요하다.
- 목표 캡처의 Port Map 번호·Signal Flow·EDID/딥 스위치 설명은 제조사별 근거가 필요하다. 번호 카드와 디자인은 재사용하지만 현재 240개에 추측으로 도식화하지 않는다.

### 연결 단자와 검증 정보 보존

- `quantity`에는 숫자 포트 수뿐 아니라 `2 stereo pairs / 4ch` 같은 문자열이 존재한다. 새 IN/OUT 알약에 raw quantity를 포트 수처럼 붙이면 기존에 해결한 혼동이 재발한다. `connectorPresentation`의 portCount·channelSignal·specificationCondition·flags를 보존한다.
- BNC만으로 SDI, RJ-45만으로 네트워크, XLR만으로 오디오라고 확정하면 틀린다. 현재 H5의 BNC는 Genlock IN/LOOP이고 RJ-45에는 RS-232도 있다. **signal/protocol 우선**, 불명확한 색은 중립색을 사용한다.
- 카드 말줄임 아래에서도 중요한 옵션·카드 필요·모델 적용 조건을 읽을 수 있어야 한다. 전체 단자 표에는 source·verification 등 근거 접근을 유지한다.
- 패키지 배지를 하단으로 이동하는 것은 데이터 VERIFIED 전환이 아니다. 중요 충돌·기능 적용 제한은 해당 수치 곁에 남기고 상세 근거를 하단에 둘 것을 권고한다.
- 원문 기록 영역은 issues·MISSING 문서·imageStatuses 중심이다. REVIEW REQUIRED/CONFLICTED 문서, 실제 images의 권리/출처, 사양·I/O의 source/verification를 빠뜨리지 않도록 보완해야 한다. 일괄 숨김으로 근거 접근이 사라져서는 안 된다.
- 외부 PDF의 내려받기 버튼은 브라우저가 다운로드를 보장하지 않는다. 기존 허용된 링크를 열도록 하고 임의 재호스팅/프록시 추가는 하지 않는다.

### 4단계: 성능 기준과 결정적 생성

- 현재 loadDetailSearchTerms는 slug별 상세 JSON을 Promise.all로 받는다. 개선 대상은 실제로 존재한다.
- generatedAt을 매 실행 현재 시각으로 생성하면 `--check`가 매번 실패할 수 있다. 안정적인 생성 기준 또는 내용 비교 규칙을 정한다.
- 정상 인덱스에서는 상세 JSON 일괄 fetch 0회를 목표로 한다. 총 요청 10회는 제품 이미지 로딩이 있는 결과 화면까지 포함하면 불가능할 수 있어 초기 데이터 요청과 이미지 요청을 따로 집계한다.
- 3단계에서 요약·사진을 보여준 뒤 4단계에서 바꾸므로 aliases·summary·cardImage·검토 중 항목의 검색 제외 정책·상세 없는 7개 항목을 모두 보존한다. 누락/손상/이전 버전 인덱스 복구도 검사한다.

### 5단계: 이름 변경보다 넓은 direction 변경

- 원문은 이름만 바꾼다고 하면서 비어 있는 direction을 채우도록 한다. direction 변경은 별도 허용 필드로 승인하거나 제외해야 한다.
- Input/Output 그룹만으로 Video·Audio 등 신호를 추론하지 않는다. 해당 행의 근거가 불충분하면 표기를 유지하고 대응표에 보류한다.
- 현재 `categories` 마지막 값 기반 아이콘과 TOP_CATEGORIES terms를 함께 검사해야 한다. 이름을 정리한 뒤 검색 결과 동일성은 승인된 대응표에 따른 차이와 회귀를 구분한다.

### 6단계: RTCOM은 파일 복사만으로 연결되지 않음

현재 RTCOM index는 **31개**, 제외 모델 4개는 목록에 없었다. 추가 차감할 이유는 없다. 오래된 upstream 인계 본문은 28개·PDF 재배포 금지라고 쓰지만 현재 HD-210U 문서 항목은 사용자 결정에 따른 제품별 PDF file을 제공한다. 첨부 최신 6단계와 실제 배포본을 시작 시 재대조해야 한다.

- 현재 Portal 검사는 허용 키를 제한하고 `presentation`을 필수로 요구한다. RTCOM에는 presentation이 없고 id·group·lead·subtitle·related·portMap 등이 추가된다. 원본을 그대로 저장한 뒤 **표시용 어댑터**에서 별도 변환해야 한다. 원본 JSON SHA 검사와 표시 객체 검사를 나눈다.
- 문서가 url이 아니라 file인 경우가 있고 images에는 publicationStatus/sourceUrl이 항상 있는 것이 아니다. 확인하지 않은 필드를 추정 VERIFIED로 채우지 않는다. 기존 이미지/링크 검사를 무력화하지 않고 RTCOM 공개 자산용 명시적 검증을 추가한다.
- images의 파일명과 로컬 URL, source code와 원문 링크, related.target과 rtcom- 접두 slug를 연결해야 한다. 원본 파일 bytes는 그대로 유지한다.
- vendor/rtcom은 Pages 배포 루트 밖이므로 어디에 공개 파생물/자산을 배치할지 정해야 한다. 원본 전체를 무검사로 배포하지 않는다.
- index만 최신이고 상세 일부가 이전인 혼합본을 방지해야 한다. 동일 배포/리비전 확인·파일별 해시·임시 다운로드 후 전체 성공 시 교체, 실패 시 마지막 정상본 보존이 필요하다.
- 추후 신규 id도 기존 제외 정책을 다시 검사한다. 사라진 id는 경고 후 사용자 결정에 따르고 자동 삭제하지 않는다.
- catalog.html·llms.txt 포함 여부는 6단계 전에 결정한다. 현재는 내부 자료/비공개 전환을 다루지 않는 최신 요청이 우선이며, upstream의 과거 사내 자료 연동 요구를 실행하지 않는다.
