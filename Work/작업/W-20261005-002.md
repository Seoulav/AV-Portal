## ★ 원본은 이렇게 생겼다 — 검토 세션이 공개 주소를 직접 읽었다

읽은 곳이다.

https://seoulav.github.io/rtcom-configurator/src/products.js

렌더러 확인본 SHA-256 `df4f5926…96694` (177,270바이트).

### 제품군 5개 + 전체

| 순서 | 원본 `group` | 표시 이름 | 항목 수 | 예 |
|---:|---|---|---:|---|
| 1 | `series` | **매트릭스 시리즈** | **3** | XDM · SPX · VDM |
| 2 | `integrated` | **일체형 매트릭스** | **2** | QMS-44UX · QMS-88UX |
| 3 | `distribution` | **분배기·선택기** | **8** | HD-104U · HD-108U · HDS-42MU |
| 4 | `extender` | **전송기** | **15** | XDM-CTR100 · SPX-RX/TX · XDM-PSU |
| 5 | `cable` | **케이블** | **4** | AHOC · HOC-UX · LHOC · UMC |

**`전체`는 6번째 제품군이 아니다.** 32개를 한꺼번에 보는 것이다.

### ★ Work가 저장소 사본으로 대조했다

검토 세션이 읽은 것은 **원격**이다. 나는 **우리 사본**을 열어 같은지 봤다.

```
beta/site/rtcom/raw/index.json
  schema     rtcom.products.v1
  groups     series=매트릭스 시리즈 · integrated=일체형 매트릭스
             distribution=분배기·선택기 · extender=전송기 · cable=케이블
  products   32
  group별     extender 15 · distribution 8 · cable 4 · series 3 · integrated 2
```

**3 / 2 / 8 / 15 / 4 = 32.** 원격과 **같다.** 제품군 이름도 `index.groups`에 **이미 들어 있다.** 새로 수집할 것이 없다.

## ★★ 가장 조심할 것 — 「32종」이라고 쓰면 안 된다

32 중 **3개(XDM·SPX·VDM)는 시리즈**다. 한 모델이 아니다.

> **"RTCOM 독립 제품 모델 32종"은 틀린 말이다.** 「**항목 32개**」라고 쓴다.

### 시리즈 안의 행 수를 모델 수로 쓰면 안 된다

공개 시리즈 JSON의 `lineup` 행 수다.

| 시리즈 | `lineup` 행 |
|---|---:|
| XDM | 26 |
| SPX | 10 |
| VDM | 25 |

**이 행들에는 독립 제품 `id`가 없다.** 메인프레임·입출력 카드·전송기를 합한 행 수다.

> **`rtcom-xdm-…` 같은 상세 주소를 지어내지 않는다.** `id`가 없으므로 주소를 만들 근거가 없다.

### 송수신 쌍·케이블 길이도 늘리지 않는다

원본의 **항목 단위를 그대로 둔다.** SKU 단위로 쪼개 32개를 부풀리지 않는다.

## ★ 지금 우리 쪽에서 무엇이 사라지나

### 제품군 정보를 받아 놓고 버린다

`beta/site/shared/rtcom-adapter.mjs:50` `adaptRtcomCatalog`가 만드는 항목이다.

```js
{ brand:'RTCOM', product, categories, kind, official_links,
  link_scope: product.group === 'series' ? 'series' : 'model',   // :59
  slug, rtcomId, aliases, cardSummary, cardImage }
```

> **`group`이 `link_scope` 한 곳에만 쓰이고 탐색 정보로는 넘어가지 않는다.** 목록은 제품명으로 정렬되어 **원본 순서도 사라진다.**

**자료는 이미 있다. 전달만 안 하고 있다.**

### RTCOM은 `catalog.json`에 없다

`beta/site/app.js:248` `combinePublicCatalog`가 **화면에서 붙인다.**

```
catalog.json  250개 (RTCOM 0개)  +  rtcom/raw/index.json 32개  →  282개
```

**삼성과 처리 경로가 다르다.** 삼성은 `catalog.json`의 `brandSort`, RTCOM은 동기화된 `index.groups`다. 설계할 때 이 차이를 섞지 않는다.

### 제외 4종은 건드리지 않는다

`rtcom-adapter.mjs:5` `RTCOM_EXCLUDED_MODELS = ['HS-88M-U','HS-88MX','HD-D104U','HD-D108U']`

**현재 원본 32개에는 이 4종이 들어 있지 않다.** 안전장치로 남아 있을 뿐이다. **`HD-104U`·`HD-108U`와 헷갈리지 않는다.** 이름이 비슷하지만 다른 제품이고, 이 둘은 **정상 포함 대상**이다.

## 검토안 A — 제품군 탐색부터 맞춘다 (권장)

```
RTCOM → 제품군 → 항목(제품 또는 시리즈) → 상세·자료
```

1. `전체` + 원본 **5개 제품군**을 고를 수 있게 한다
2. 이름·소속은 **동기화된 `index.groups`·`product.group`에서 읽는다.** 제품명 정규식으로 **다시 분류하지 않는다**
3. 기본 순서는 **원본 순서**를 따른다. 사용자가 제품명·관련도 정렬을 고르면 **그 선택을 존중한다**
4. 기존 **상세·자료·관련 제품 링크를 유지한다.** 시리즈는 **시리즈 항목 그대로** 보여준다
5. 메인프레임·카드·구성 기능은 **원본 상세(`#products/<id>`)로 연결**해 들어가게 한다
6. 고른 상태를 **주소와 뒤로가기에 남긴다.** 제조사를 바꾸면 **RTCOM 제품군 선택을 푼다**

**이것은 보여주는 정보를 더하는 일이다.** 제품 기술 사양이나 원본 구조를 확정·변경하는 일이 아니다.

## 검토안 B — 시리즈 상세까지 가져온다 (별도)

XDM 같은 시리즈의 **메인프레임·입출력 카드 선택을 포털 안에서** 하고 싶을 때다.

### ★ 왜 간단하지 않은가

원본 `seriesDetailView`는 **두 곳에서 자료를 가져온다.**

| 출처 | 내용 |
|---|---|
| `item.lineup` | 메인프레임 등 |
| **`window.RtCatalog[family].input / output`** | **카드 라인업** |

**카드 이미지와 누르면 뜨는 창은 제품 `index`/`detail` JSON만으로 전달되지 않는다.**

> 어댑터에 `lineup` 하나를 더했다고 **원본의 시리즈 선택 기능을 구현한 것이 아니다.**

B를 한다면 **읽기 전용으로 보이는 범위**와 **팝업·이미지·자료·구성 진입까지 재현하는 범위**를 **먼저 나눈다.** 새 공개 데이터 계약·자산 경로·개정 관리가 필요하다.

### 통째로 가져오는 것은 권장하지 않는다

원본 iframe 끼우기나 구성기 코드 복사는 **첫 단계로 권하지 않는다.** 포털의 검색·상태 복원과 원본의 상태를 **둘 다 관리**해야 하고, 제품군 분류를 살리는 것보다 **범위가 훨씬 커진다.**

## ★ 동기화 — 지금 손으로 덮어쓰면 안 된다

조사 시점의 SHA-256이다.

| | |
|---|---|

| 우리 `SYNC.json` 기록 | `eda6f6cb3322b513b982760083fb3f80eb37951dbe852067baf78676bb944d62` |

**다르다.** 대조 결과다.

- 항목 수 **32**, `id` 순서, 그룹 이름·소속 **같다**
- 추가·삭제된 `id` **없다**
- **26개 항목의 `english` 또는 `korean` 요약 문구만 다르다**
- 목록 최상위 필드 변경 없다

> **그룹 구조 검토는 이대로 진행해도 된다.** 양쪽 분류가 같기 때문이다.

**문구 차이를 손으로 `raw`에 덮어쓰지 않는다.** 정상 동기화 절차로 반영한다. 이번 검토에서는 **동기화를 실행하지 않았다.**

### 옛 문서를 기준으로 삼지 않는다

> `Work/작업/av-portal-redesign-20260929/06_RTCOM_INTEGRATION.md`의 **「수동만」·「31종」은 그때의 계획**이다. **지금 기준으로 복원하지 않는다.**

## ★ 삼성 001과의 관계 — 상태 계약만 맞추고 범위는 나눈다

[W-20261005-001](W-20261005-001.md)이 **제조사 안에서 묶음을 고르는 단계**를 먼저 만든다. RTCOM 제품군 선택은 **구조가 같은 일**이다.

**두 개의 서로 다른 장치를 만들지 않는다.**

| | 삼성 001 | RTCOM 002 |
|---|---|---|
| 묶음의 출처 | `catalog.json`의 `brandSort.group` | 동기화된 `index.groups` · `product.group` |
| 묶음 이름 | 고정 표 | **동기화 자료에서 읽음** |
| 주소 상태 | `series` | **같은 `series`를 쓴다** |
| 지워지는 규칙 | 001이 정한 9가지 | **그대로 따른다** |

> **001은 `beta/site/shared/brand-series.mjs`를 제조사별로 갈라지는 모양으로 만든다.** 002가 RTCOM 갈래를 더할 때 **001을 다시 쓰지 않아도 되게** 한다. 001에서 RTCOM을 **구현하지는 않는다.**

**범위는 독립이다.** 001이 병합된 뒤 그 위에서 002를 설계한다.

## 실행 명세로 옮길 때 넣을 검증 조건

- 제품군별 **3 / 2 / 8 / 15 / 4 · 합계 32**. **실제 목록에서 세어** 비교한다. 미래에 제품이 늘어나는 것을 **영구 고정 수치로 막지 않는다**
