## 왜 하는가

[W-20261004-015](W-20261004-015.md)에서 Codex가 AEC를 일부러 뺐고, 근거를 남겼다.

> *"AEC 처리 채널 12는 사양에 있지만 I/O 행이 아닌 처리 기능이므로 이 단자 경로 그림에는 넣지 않았습니다."*

**판단은 옳았다.** 그 그림은 단자 경로도였다. 사용자가 **처리 흐름도로 바꾸라**고 정했다. BLU-101은 AEC가 제품의 핵심이고, 신호가 **입력 → AEC → 매트릭스** 순으로 흐른다.

---

## 1 — ★ AEC 블록은 BLU-101 **하나뿐**이다

BSS 5종의 사양 행을 전부 읽었다. **데이터가 경계를 이미 그어 놓았다.**

| 제품 | AEC 사양 행 | 블록 |
|---|---|:--:|
| **`blu-101`** | **`AEC 처리 채널 = 12 채널(독립 알고리즘)`** (`specifications[3]`, FOUND) | **넣는다** |
| `blu-100` | **`AEC 지원 = 없음`** (`specifications[3]`, FOUND) | **넣지 않는다** |
| `blu-50v2` | **`AEC 입력 = 0`** (`specifications[5]`, FOUND) | **넣지 않는다** |
| `blu-160` | `AEC 입력(최대) = 최대 16` — **카드 구성에 따라 달라진다** | **넣지 않는다** |
| `blu-dan` | AEC 사양 **없음** | **넣지 않는다** |

**`blu-100`과 `blu-101`은 뒷면이 똑같고 `io`도 똑같다.** 두 제품을 가르는 것이 바로 이 AEC다. 보이는 모양이 비슷하다고 같이 고치면 **없는 기능을 그리게 된다.**

`blu-160`은 **최대치이지 구성값이 아니다.** 「카드 구성별 DSP」라는 지금 블록이 맞다.

### 근거는 이미 통과한다

`validEvidence`는 `{ kind: 'spec', index: N }`을 받는다. 조건은 **`verification`이 `VERIFIED` 또는 `FOUND`**인 것뿐이다. `blu-101`의 `specifications[3]`은 **FOUND**다. **새 사실을 만들지 않는다.**

## 2 — ★★ 지금 넣으면 03 카드가 **통째로 사라진다**

`detail-enhancements.mjs`의 `validFlow`에 이런 줄이 있다.

```js
// A crosspoint layout owns the central lane. Mixed/multiple matrices need a
// future layout contract; reject them rather than hiding overlapping blocks.
if (flow.processes.some(p => p.kind === 'matrix') && flow.processes.length !== 1) return false;
```

**매트릭스가 있으면 처리 블록은 하나여야 한다.** AEC를 더하면 `validFlow`가 `false`를 돌려주고, 03 카드가 **안 나온다.** 데이터만 고치는 일이 아니다.

막는 줄이 하나 더 있다.

```js
if (!c.inputs.every(id => flow.connections.some(e => e.from === id && e.to === p.id))) return false;
if (flow.connections.some(e => e.to === p.id && !c.inputs.includes(e.from) || …)) return false;
```

**교차점 입력 12개가 매트릭스에 직접 이어져야 한다.** `IN → AEC → 매트릭스`로 바꾸면 두 줄 다 걸린다.

### 그 주석이 말하는 **"future layout contract"를 이번에 쓴다**

작성자는 막은 이유를 적어 뒀다. **"겹치는 블록을 숨기느니 거절한다."** 레이아웃이 없어서 막은 것이지, 틀려서 막은 것이 아니다.

**레이아웃을 만들어 빗장을 연다.** 여는 범위를 정확히 좁힌다.

| | |
|---|---|
| 연다 | 매트릭스 **앞단**에 처리 블록이 오는 경우 |
| **계속 막는다** | 매트릭스 **2개 이상** |
| **계속 막는다** | 블록이 **겹쳐 그려지는** 어떤 경우든 |

### 교차점 조건을 어떻게 고치나

**"직접 이어져 있다"를 "앞단을 지나 닿는다"로 바꾼다.** 느슨하게 푸는 것이 아니라, **경로를 따라가 확인**하는 것이다.

- `c.inputs`의 12개가 **매트릭스까지 가는 길이 실제로 있는지** `connections`를 따라 확인한다
- 길이 없는 입력이 교차점에 적혀 있으면 **여전히 거절**한다
- 매트릭스로 들어오는 선 중 **교차점에 없는 입력에서 온 것**이 있으면 **여전히 거절**한다

**검사가 약해지면 안 된다.** 거리를 1칸에서 여러 칸으로 늘리는 것뿐이다.

## 3 — 그림을 어떻게 그리나

### 지금 자리

```
x  12…152      198…418                 604…784      (W = 800)
   입력 12       매트릭스 12×8              출력 8
```

처리 블록은 **세로로 쌓인다**(`processY += h + 36`). 블록끼리는 **세로 화살표**로 잇는다. `dci-4-600da`가 3단(`select → dsp → amplify`)을 그렇게 그린다.

**AEC를 그렇게 쌓으면 안 된다.** 매트릭스는 **가로줄이 입력 칸 높이에 맞춰** 그려진다(`ys = c.inputs.map(…)`). AEC를 위나 아래에 두면 그 정렬이 깨지고, **"입력 → AEC → 매트릭스"로 읽히지 않는다.**

### 넣을 자리 — 입력과 매트릭스 **사이 세로 띠**

```
   입력 12 ──┤ AEC ├── 매트릭스 12×8 ───── 출력 8
              12채널
```

- 12개 가로줄이 **AEC 띠를 지나** 매트릭스로 들어간다
- AEC는 **입력 12행 전체 높이**를 덮는 세로로 긴 둥근 사각형
- 폭이 좁으니 **글자를 어떻게 넣을지는 Codex가 정한다.** 세로 쓰기·두 줄·띠 위 라벨 중 읽히는 쪽

지금 입력 오른쪽 끝(152)과 매트릭스 왼쪽(198) 사이가 **46px뿐**이라 그대로는 못 들어간다. **`W`를 넓히거나 매트릭스를 오른쪽으로 밀어야 한다.** 둘 중 **기존 8종이 안 변하는 쪽**을 고른다.

### 알티컴에는 이 경우가 없다

알티컴 `ioFlowDiagram`은 **매트릭스 앞단 블록을 그리지 않는다.** 베낄 원본이 없다. **알티컴의 선·색·글자 규격을 쓰되 배치는 새로 만든다.**

## 4 — 알티컴과 지금 무엇이 다른가

사용자가 지목한 **출력 가로축**과 **범례**를 포함해 전부 대조했다.

### 출력 가로축 — 사용자가 지목

| | 알티컴 (`products.js:221`) | AV-Portal (`detail.css:211`) |
|---|---|---|
| 번호 | `font-size 9` · `font-weight 700` · `#8944AB` | **`12px` · 기본 굵기 · `#53667b`** |
| 세로 격자선 | `#BF5AF2` · `width 1.2` · `opacity .35` | `#9860b6` · `width 1` · `opacity .4` |
| 가로 격자선 | `#007AFF` · `width 1.2` · `opacity .35` | `#4a90db` · `width 1` · `opacity .4` |

**번호가 우리 쪽이 많이 크고 흐리다.** 알티컴은 작고 진한 보라로 **축이라는 것이 드러난다.**

### 교차점·상자

| | 알티컴 | AV-Portal |
|---|---|---|
| 선택 점 | `r 5` · `#8944AB` | `r 5` · `#884bae` |
| 비선택 점 | `r 2` · `#C7C7CC` | `r 2` · `#c8d3e1` |
| 상자 | `stroke #007AFF` · **`width 3`** · `rx 14` | `stroke #b5c7e0` · **`width 1.6`** · `rx 16` |
| 상자 제목 | `font-size 12` · `weight 800` · `#007AFF` | `14px` · `750` · `#263d58` |
| 선택 예시 | `10` · `600`, **`●`만 보라** | `12px`, **전체 보라** |
| 입력 화살촉 | **상자 직전에 있다** | 없다 |
| 상자 안 아래 | **`출력마다 입력 선택`** | `caption`으로 처리 |

**상자 테두리가 3 대 1.6으로 거의 두 배 차이**다. 화면에서 가장 크게 다른 것이 이것이다.

### 케이블 범례 — 사용자가 지목

| | 알티컴 (`styles.css:561·611`) | AV-Portal (`detail.css:226`) |
|---|---|---|
| 짜는 기준 | **경로의 뜻** — `영상` · `오디오 추출(점선)` · `멀티뷰 분기(점선)` | **신호 종류** — `아날로그 오디오` |
| 보조 경로 | **항목마다 이름이 붙는다** | `┄ 보조 경로` **한 줄로 뭉친다** |
| 점선 표시 | `width 16` · `border-top 2px dashed` | 없음 |
| 색칸 | **`9×9` 사각** | `17×3` 막대 |
| 글자 | `11.5px` · `600` | `13px` |
| 영상 색칸 | **`#0A84FF → #BF5AF2` 그라데이션** | 단색 |
| 윗선 | 없음 | `border-top 1px #e5eaf1` |

**알티컴 범례는 "이 선이 무슨 뜻인가"를 적고, 우리 것은 "무슨 신호인가"를 적는다.** 보조 경로가 여럿일 때 우리는 전부 `┄ 보조 경로` 하나로 뭉쳐 **어느 점선이 무엇인지 알 수 없다.**

**`ulxd4d`가 보조 경로 4개**를 그렇게 뭉쳐 놓았다. 가장 먼저 좋아질 제품이다.

### ★ 지금 데이터로 할 수 있는 것과 없는 것

`legend` 항목은 `{ signal, label }`뿐이라 **점선 여부를 적을 자리가 없다.**

- `label`은 **이미 자유 문구**다. `'영상 · 점선은 모니터링'`처럼 쓰고 있다
- **`auxiliary` 선의 `label`에 뜻이 이미 적혀 있다.** 범례를 **그 `label`에서 뽑아내면 데이터를 안 고쳐도 된다**
- 그래도 모자라면 **`legend`에 선택 항목을 더해도 된다.** 다만 **기존 8종이 그대로 통과**해야 한다

**어느 쪽이든 새 사실을 만들지 않는다.** 범례 글귀는 이미 데이터에 있는 말이다.

## 5 — BLU-101에 없는 것은 만들지 않는다

사용자가 보여 준 알티컴 화면에는 **대역폭 띠**(`4K/60 @ 4:4:4`), **동작 모드 선택**, **멀티뷰 분기**, **오디오 추출**이 있다.

**BLU-101에는 이 중 어느 것도 없다.** 오디오 DSP이지 영상 매트릭스가 아니다.

| 알티컴 화면의 요소 | BLU-101 |
|---|---|
| 대역폭·해상도 띠 | **없다.** `band`를 만들지 마라 |
| 동작 모드 선택 | **없다** |
| 멀티뷰 분기(점선) | **없다** |
| 오디오 추출(점선) | **없다.** `auxiliary`가 **0건**이다 |

**디자인을 따라하는 것이지 내용을 따라하는 것이 아니다.** BLU-101 범례는 `아날로그 오디오` 한 줄이 맞다. 억지로 늘리지 마라.
