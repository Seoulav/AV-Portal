## 알티컴은 데이터를 쓰지 않는다

`rtcom-configurator/src/products.js:591`

```js
function connectionDiagram(item){
  if(item.group==='cable')     return cableDiagram(item);
  if(item.group==='distribution'||item.group==='integrated') return ioFlowDiagram(item);
  if(item.id==='xdm-psu')      return psuDiagram(item);
  if(item.group==='extender')  return extenderDiagram(item);
  return null;
}
```

`ioFlowDiagram()`이 **`io`에서 입력 수·출력 수·오디오 유무를 읽어** 그린다. 소스 주석이 못 박는다.

> *"입력 수·출력 수·오디오는 io 데이터에서 뽑는다(**새 사실을 만들지 않음**)"*

매트릭스인지 분배기인지도 추론한다.

```js
const isMatrix = inN>1 && outN>1 && (item.group==='integrated' || /matrix|매트릭스/i.test(…));
```

우리 `signalFlow`(`validFlow`)는 **모든 노드와 선에 `evidence`를 요구**하는 손 작성 방식이다. 둘은 접근이 다르다.

## ★ 그릴 것 — 12×8 매트릭스

사용자가 **"BLU-101은 12 곱하기 8이야"**라고 바로잡았다. 초판은 가운데를 **"DSP 처리"**로 뭉뚱그렸는데 **그게 핵심을 놓친 것**이다.

**BLU-101은 12입력 × 8출력 매트릭스다.** 어느 입력이든 어느 출력으로 보낼 수 있다는 것이 이 제품의 성격이고, 그림이 그걸 보여야 한다.

```
아날로그 입력 12  ─┐
BLU link 입력    ─┼─→  [12 × 8 매트릭스]  ─┬─→ 아날로그 출력 8
                                           └─→ BLU link 출력
```

### 필요한 것이 이미 다 있다

| 필요 | 어디에 |
|---|---|
| `matrix` 처리 종류 | **`processKinds`에 있음** |
| 교차점 구조 | **`crosspoints: { inputs, outputs, examples }`** |
| `audio-dsp` 흐름 유형 | `flowTypes`에 있음 |

`crosspoints`는 **어느 입력이 어느 출력으로 갈 수 있는지**를 담는다. `examples`로 **실제 연결 예시**를 보여 줄 수 있다. 12×8 매트릭스를 표현하기에 맞는 구조다.

### 지킬 것

- 입력·출력 **수량은 `io`에서 읽는다.** 지어내지 않는다
- **`examples`는 동작 예시임이 드러나야 한다.** 고정 결선이 아니다. 시범 제품 `dci-4-600da`의 `description`이 **"선택 점은 동작 예시입니다"**라고 적고 있다. 같은 방식을 쓴다
- 제어 단자(Ethernet·RS-232·GPIO)는 **신호 경로가 아니다.** 보조선으로 두거나 뺀다
- `blu-101`은 **AEC가 핵심**이나 `io`에 없고 **사양 행에 `AEC 처리 채널 = 12`**가 있다. 매트릭스 앞단에 넣을지 판단해 보고한다

### 5종이 서로 다르다

| 제품 | 구조 |
|---|---|
| `blu-101` · `blu-100` | **12 × 8 매트릭스** |
| `blu-50v2` | 4 × 4 |
| `blu-160` | **카드 구성에 따라 달라짐** — 최대 16 × 16 |
| `blu-dan` | **매트릭스가 아니다.** Dante ↔ BLU link **브리지** |

**`blu-dan`은 `bridge` 처리 종류**가 맞다. `processKinds`에 있다. 억지로 매트릭스로 그리지 마라.

## ★ 두 방식 중 하나를 고르는 것이 이번 산출물

| | 우리 `validFlow` | 알티컴 `ioFlowDiagram` |
|---|---|---|
| 데이터 | 제품마다 손 작성 | **불필요** |
| 근거 | 노드·선마다 `evidence` | `io` 행 자체 |
| 유연성 | 내부 구조까지 | `io`가 표현하는 수준 |

**5종을 해 보고 어느 쪽이 맞는지 판단해 보고하라.** 그 판단이 나머지 49종의 방식을 정한다.

- `validFlow`를 쓰면 **`evidence`가 `io` 행을 가리키면 된다.** 손 작성이지만 근거가 붙는다
- 자동 생성을 쓰면 **새 코드가 필요하고 검증기를 안 거친다**

**어느 쪽이든 새 사실을 만들지 않는다.**
