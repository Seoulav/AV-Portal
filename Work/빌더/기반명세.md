## 2. 표준 어휘와 변환 규칙

`beta/port-vocabulary.mjs`는 이 절의 규칙을 **위에서 아래 순서로** 적용한다. 앞에서 정해지면 뒤 규칙은 보지 않는다. 판단할 수 없는 행은 메우지 않고 "확인 필요"로 남긴다.

### 2.3 신호

**찾는 순서**

1. `signal` 칸에서 찾는다.
2. 하나도 못 찾았을 때만 `connector` 칸에서 찾는다.
3. `protocol` 칸은 이미 찾은 신호가 네트워크 계열이거나 커넥터가 `RJ45`·`SFP`일 때, 네트워크 계열 신호(`DANTE`·`AES67`·`COBRANET`·`POE`·`HDBASET`·`ETHERNET`)를 **덧붙이는 데만** 쓴다.
4. 그래도 없으면 커넥터가 신호를 정의하는 경우만 채운다.
   - `HDMI`→`HDMI`, `DP`→`DP`, `DVI`→`DVI`, `SPEAKON`→`SPEAKER`, `USB-*`→`USB`

`group` 칸은 쓰지 않는다. "Audio Network" 같은 묶음 이름이 아날로그 단자에 네트워크 신호를 잘못 붙였기 때문이다.

**후처리**

- `DANTE`·`AES67`·`COBRANET`·`AVB`·`POE`가 있으면 `ETHERNET`을 덧붙인다. 일반 네트워크 스위치와 연결되게 하기 위해서다.
  - `BLU-LINK`와 `HDBASET`에는 붙이지 않는다. 이더넷 스위치에 꽂는 신호가 아니다.
- `POWER`와 `USB`가 함께 있으면 `USB`를 주 신호(앞)로 옮긴다. USB 전원 출력 단자가 전원선으로 숨지 않게 하기 위해서다.
- signal 칸에 ` 또는 `·`or`·`멀티뷰어`가 있고 신호 계열이 둘 이상이면 **확인 필요**(`multi-signal`)로 보낸다. 예: `SFP / 추가 SDI, HDMI 또는 64채널 MADI`

`AVB`는 이번 데이터에 없지만 표준값으로 둔다.

### 2.4 방향

| 원문 | 표준값 |
|---|---|
| `IN`, `입력` | `in` |
| `OUT`, `출력` | `out` |
| `IN/OUT`, `I/O`, `BIDIR`, `양방향` | `both` |
| 빈칸·`N/A`·`정보 없음` + 신호가 모두 대칭 신호(`ETHERNET`·`DANTE`·`AES67`·`AVB`·`COBRANET`·`BLU-LINK`·`POE`) | `both` (5행) |
| 그 밖의 빈칸·`N/A`·`정보 없음`, `IN/LOOP` | 확인 필요 |

대칭 신호는 단자 자체에 방향이 없어서 `both`로 둔다. 이것은 추정이 아니라 신호의 정의다.

- 보강은 두 가지 방법 중 하나로 한다.
  1. Portal 상세 데이터의 해당 행을 제조사 자료로 고친다. 기존 Portal 데이터 절차를 따른다.
  2. 원문이 맞는데 규칙으로 못 읽는 경우는 `port-vocabulary.mjs`의 **개별 지정**(제품 ID + 행 위치 → 표준값)에 근거와 함께 추가한다. 예: `BNC / 디지털 비디오 입력`을 SDI로 지정하려면 제조사 자료 확인이 필요하다.

### 2.7 커넥터 간 호환 묶음

연결 규칙의 `connector-adapter` 경고(§7)에서 **같은 커넥터로 보는** 묶음이다.

| 묶음 | 이유 |
|---|---|
| `USB`와 모든 `USB-*` | `USB`는 형태 미상이라 다르다고 단정할 수 없다 |
| `IEC`와 모든 `IEC-*` | 같은 이유 |
| `XLR`·`XLR-COMBO`, `TRS-6.3`·`XLR-COMBO` | 콤보 잭은 XLR과 6.3mm 플러그를 모두 받는다 |
| `UNKNOWN`·`CAPTIVE`와 아무 커넥터 | 모르는 것을 다르다고 하지 않는다. 대신 `connector-unknown` 안내(info)를 남긴다 |

## 3. 단자 ID와 이름

### 3.1 ID 형식

```
<direction>-<신호키>-<n>
```

| 부분 | 값 | 예 |
|---|---|---|
| `direction` | `in` · `out` · `both` (1.1 형식과 같음) | |
| `신호키` | §2 표준 신호의 소문자 키. 영숫자와 하이픈만 | `hdmi`, `sdi`, `dante`, `line-audio`, `rs-232` |
| `n` | 같은 `direction`·`신호키` 안에서 1부터 매기는 번호 | `in-hdmi-1`, `in-hdmi-2`, `out-hdmi-1` |

- 단자의 신호가 여러 개면(예: RJ45 = `ETHERNET` + `POE`) **첫 번째 신호**가 신호키가 된다. 신호 순서는 §2 대응표에 적힌 순서다.
- 영숫자·하이픈 외의 문자는 쓰지 않는다. 구 데이터의 `out-hdmi out-1` 같은 공백 오류를 막기 위해서다.
- 한 노드 안에서 유일하다. 노드가 달라도 같은 ID가 나올 수 있다. 1.1과 같다.

### 3.2 번호 매기는 순서

1. 상세 JSON `io[]`의 **행 순서**를 따른다.
2. 한 행의 `quantity`가 N이면 그 행에서 N개를 연속으로 매긴다.
3. 같은 방향·신호키가 여러 행에 나뉘어 있으면 앞 행부터 이어서 매긴다.
   - 예: `Front · HDMI IN 1`, `Rear · HDMI IN 2` → `in-hdmi-1`, `in-hdmi-2`, `in-hdmi-3`

Portal에서 행 순서를 바꾸거나 수량을 고치면 번호가 바뀔 수 있다. 이미 저장한 구성도는 노드가 배치 당시 단자를 품고 있어 계속 열린다. 차이는 `library-drift` 이슈로 알린다(통합 기획 §6.4). P5에서 "현재 라이브러리로 단자 다시 맞추기" 도구를 둔다.

### 3.3 이름 (`label`)

**기본 이름:** `<표준 신호 표시명> <In|Out|I/O> <n>`

- 예: `HDMI In 1`, `Dante I/O 1`, `Line Audio Out 2`
- 1.1 운영 데이터의 이름 형식("SDI Out 1", "LAN 1")과 같은 모양이다.

**같은 방향·신호가 여러 그룹에 있을 때:** 원문 `group` 앞부분을 괄호로 붙여 구분한다.

- 예: `HDMI In 1 (Front)`
- 붙이는 기준: 같은 방향·신호키의 단자가 서로 다른 `group`에서 나온 경우만

**Port Map 이름:** P2 이후 `beta/builder-port-links.mjs`에 대응을 적은 제품은 Port Map의 `label`을 쓴다.

- 예: `HDMI 1 입력`
- 대응표 형식: `{ productId: { "in-hdmi-1": 1, "in-hdmi-2": 2 } }` (단자 ID → Port Map 번호 `n`)
- 사람이 사진과 I/O 행을 보고 채운다. 이름이 비슷하다고 자동으로 짝짓지 않는다.

### 3.4 단자에 붙는 추가 필드 (1.2)

```json
{ "id": "in-hdmi-1", "label": "HDMI In 1", "type": "video", "direction": "in",
  "connector": "HDMI", "signals": ["HDMI"], "verification": "FOUND",
  "portal": { "group": "Video", "connector": "HDMI", "signal": "디지털 비디오 입력" } }
```

| 필드 | 1.1에 있음 | 뜻 |
|---|---|---|
| `id`, `label`, `type`, `direction` | ✓ | 1.1과 같다. `type`은 선 종류 ID(§5) |
| `connector` | | 표준 커넥터(§2) |
| `signals` | | 표준 신호 목록(§2). 첫 번째가 주 신호 |
| `verification` | | 원본 I/O 행의 검증 상태 그대로 |
| `portal` | | 원본 I/O 행의 `group`·`connector`·`signal` 원문. 사람이 근거를 찾아가는 용도 |

## 4. 카테고리 대응

### 4.1 기준

- **기준은 `catalog.json`의 `categories`(3단계)다.** 상세 JSON의 `categories`는 쓰지 않는다.
  - 267건 모두 3단계가 채워져 있다.
  - 상세 JSON 40건은 목록과 다르게 적혀 있다. 단계가 둘뿐이거나(`["오디오","Audio Processor"]`) 이름이 다르다(`PTZ/원격 카메라`).
- RTCOM은 `rtcom/raw/index.json`의 `categories`를 쓴다. 모두 2단계가 `Video`다.

### 4.2 1.1 필드로 옮기는 규칙

| 1.1 필드 | 값 | 비고 |
|---|---|---|
| `category` | 2단계를 소문자로: `Audio`→`audio`, `Video`→`video`, `Display`→`display`, `Conferencing`→`conferencing`, `Control`→`control`, `Network`→`network` | 1.1 열거값 8종 중 6종을 쓴다. `broadcast`·`etc`는 쓰지 않는다 |
| `name` | 3단계 이름 그대로(예: `Amplifier`, `Wireless Microphone System`, `Extender`) | 1.1의 사이드바 중분류 자리다. Portal에 한글 3단계 이름은 없다 |

- 2단계 분포(목록 267건): Audio 104, Video 62, Display 58, Conferencing 25, Control 9, Network 9
- 3단계는 목록 51종, RTCOM 11종이다.

### 4.3 배치 대상에서 빼는 분류

다음 분류는 장비 노드가 아니다. **장비 목록(사이드바)에서 빼고** 쓰임에 맞는 곳에서 고른다.

그 밖의 액세서리·전원 장치(`Microphone Accessory`, `Power Supply`, `Power Conditioner`, `Antenna`)는 단자가 있으면 노드로 배치할 수 있다.

## 6. TX/RX 쌍과 시리즈 제품

### 6.1 TX/RX로 나누는 제품 (10종)

다음 RTCOM 제품은 모든 I/O 행의 `group`이 `TX · …` 또는 `RX · …`로 시작한다. 이 접두어로 **배치 단위 2개**를 만든다.

| 제품 ID | 원래 `model` | TX 단위 모델 | RX 단위 모델 |
|---|---|---|---|
| `rtcom-ct101-u-cr101-u` | CT101-U / CR101-U | CT101-U | CR101-U |
| `rtcom-ct103-u-h-cr103-u` | CT103-U-H / CR103-U | CT103-U-H | CR103-U |
| `rtcom-ct104-u-cr104-u` | CT104-U / CR104-U | CT104-U | CR104-U |
| `rtcom-ft101-u-fr101-u` | FT101-U / FR101-U | FT101-U | FR101-U |
| `rtcom-ft103-u-h-fr103-u` | FT103-U-H / FR103-U | FT103-U-H | FR103-U |
| `rtcom-xdm-ct103-cr103` | XDM-CT103 / XDM-CR103 | XDM-CT103 | XDM-CR103 |
| `rtcom-xdm-ft101-fr101` | XDM-FT101 / XDM-FR101 | XDM-FT101 | XDM-FR101 |
| `rtcom-spx-rx-tx` | SPX-TX / SPX-RX | SPX-TX | SPX-RX |
| `rtcom-obhd-2c` | OBHD-2C | OBHD-2C (TX) | OBHD-2C (RX) |
| `rtcom-obux-1c` | OBUX-1C | OBUX-1C (TX) | OBUX-1C (RX) |

**규칙**

- **단위 모델명:**
  - `model`에 ` / `가 있으면 앞이 TX, 뒤가 RX다.
  - 위 표 8종은 `condition`에 적힌 모델명(`CT101-U`, `CR101-U` …)과도 일치한다.
  - ` / `가 없으면 `<model> (TX)`·`<model> (RX)`로 둔다.
- **배치 단위 ID:** `<제품ID>:tx`, `<제품ID>:rx`. 노드 `data.portal.unit`에는 `tx`·`rx`를 둔다.
- **단자 이름:** `group`의 `TX · `·`RX · ` 접두어를 떼고 만든다.
- **사이드바:** 제품 하나 아래 TX·RX 두 항목으로 보인다.
- **분리 근거:** I/O 행 접두어가 **전 행에 빠짐없이** 있을 때만 나눈다. 일부 행에만 있으면 나누지 않고 확인 필요로 둔다.

### 6.2 나누지 않고 보류하는 제품

| 제품 ID | 이유 |
|---|---|
| `rtcom-xdm-ctr100`, `rtcom-xdm-ctr100-pse` | 한 대가 설정에 따라 TX도 되고 RX도 된다(`TX/RX 설정에 따라 송신 또는 수신`). 배치할 때 사용자가 모드를 고르게 할지는 제품 결정이 필요하다. 1단계에서는 한 단위로 두고 전송 단자는 `both`로 둔다 |
| `rtcom-spx-r6` | TX·RX 모듈을 칸마다 꽂는 랙 프레임이다. 카드 구성과 같은 문제라 P9로 미룬다 |

일반 제품 상세에서도 `TX`·`RX`라는 말이 나오는 36건을 확인했다. 모두 RS-232 핀 이름(Tx·Rx)이나 전원 조건 설명이라 배치 단위를 나눌 대상이 아니다.

### 6.3 시리즈 제품

- `rtcom-xdm`·`rtcom-spx`·`rtcom-vdm`은 `itemType: SERIES`이고 **I/O 행이 0개**다.
- 모델 목록(`lineup`)과 카드 설명은 있지만 카드별 단자가 없다.
- 그래서 1단계에서는 다음과 같이 처리한다.
  - 시리즈를 배치하면 `lineup`에서 모델을 고르게 한다(`data.portal.variant`, 배치 단위 ID `<제품ID>:<모델 소문자>`).
  - **단자 없이** `no-ports`·`series-config-pending` 이슈와 함께 놓인다.
  - 매트릭스를 결선하려면 RTCOM 원본(`rtcom-configurator`)에 프레임·카드 단위 I/O가 먼저 필요하다. RTCOM 원본은 Portal에서 고치지 않는다(AGENTS.md).

## 7. 연결 규칙

### 7.1 판정표

"출발"은 사용자가 선을 끌기 시작한 단자, "도착"은 놓은 단자다.

**판정 순서:** 아래 순서로 처음 걸리는 차단에서 멈춘다. 경고는 차단이 없을 때 해당하는 것을 모두 붙인다.

| 순서 | 처리·조건 | 판정 | 이슈 코드 |
|---|---|---|---|
| 0 | 출발이 `in`이고 도착이 `out`·`both`이면, 또는 출발이 `both`이고 도착이 `out`이면 **출발과 도착을 바꾼다** | — | — |
| 1 | 출발 또는 도착 단자에 이미 엣지가 있다 | **차단** | `port-occupied` |
| 2 | 같은 노드의 단자끼리 | **차단** | `self-loop` |
| 3 | 공통 신호도 없고, §7.2 레벨 차이 쌍도 아니다 | **차단** | `signal-mismatch` |
| 4 | 방향이 `in→in` 또는 `out→out`이다. **단, 공통 신호에 대칭 신호(§2.4)가 있으면 검사하지 않는다** | **차단** | `direction` |
| 5 | 연결 신호가 `POWER`이고 전원 결선이 꺼져 있다 | **차단** | `power-disabled` |
| 6 | 커넥터가 다르다. §2.7 호환 묶음은 같은 것으로 본다 | 경고 | `connector-adapter` |
| 7 | 어느 쪽 커넥터가 `UNKNOWN`·`CAPTIVE`다 | 안내 | `connector-unknown` |
| 8 | 연결 신호가 §7.2 레벨 차이 쌍이다 | 경고 | `signal-level` |
| 9 | 어느 단자의 검증 상태가 `VERIFIED`·`FOUND`가 아니다 | 경고 | `unverified-port` |

**방향**

- 0번을 거친 뒤 허용되는 조합은 `out→in`, `out→both`, `both→in`, `both→both`다.
- 0번 덕분에 사용자는 어느 쪽에서 선을 그어도 된다. 저장된 엣지의 `source`는 항상 신호를 내보내는 쪽이다.
- 대칭 신호는 실물 단자에 방향이 없다. 예를 들어 디스플레이 LAN이 `IN`으로 적혀 있어도 다른 장비의 `IN` LAN과 직접 연결할 수 있다.
  - 이번 데이터에서 네트워크 스위치 단자는 모두 `both`라 일반 결선에는 영향이 없다.
  - 이 예외는 스위치 없이 직접 연결하는 경우를 위한 것이다.

**연결 신호 (`data.signal`)**

- 공통 신호 중 출발 단자의 `signals` 순서에서 가장 앞선 것이다.
- 레벨 차이 쌍으로 연결된 경우는 출발 단자의 신호다.

### 7.2 레벨 차이 쌍

| 쌍 | 이유 |
|---|---|
| `LINE-AUDIO` ↔ `MIC-AUDIO` | 실제로 자주 연결하지만 레벨 설정이 필요하다 |

이 표에 없는 서로 다른 신호는 연결할 수 없다(3번).

## 8. 구성도 JSON 1.2 확정 명세

### 8.1 최상위

키 순서는 아래와 같다. 1.1에 있던 키가 먼저 오고, 추가 키가 뒤에 온다.

```json
{
  "version": "1.2",
  "nodes": [],
  "edges": [],
  "lineTypes": [],
  "equipmentDB": [],
  "generator": { "app": "av-portal-builder", "version": "0.1.0" },
  "library": { "schemaVersion": "1.0.0",
               "source": { "catalogSha": "…", "detailSetSha": "…", "rtcomSha": "…", "vocabularyVersion": "1.0.0" } },
  "issues": []
}
```

| 키 | 1.1 | 1.2 값 |
|---|---|---|
| `version` | `"1.1"` | `"1.2"` |
| `nodes` | ✓ | §8.2 |
| `edges` | ✓ | §8.3 |
| `lineTypes` | 운영 7종 전체 | 기존 7종 + 쓰인 새 ID. `id` 순 |
| `equipmentDB` | 로컬 카탈로그 전체(674개) | **이 구성도에 쓴 배치 단위만**(C3). `id` 순. 노드 `data`에서 `isReused`를 뺀 장비 정보 |
| `generator` | | 만든 앱과 버전 |
| `library` | | 어느 Portal 데이터로 만들었는지. SHA 계산 방법은 P2에서 정한다 |
| `issues` | | §8.5 |

### 8.2 노드

**장비 노드:**

```json
{
  "id": "node_01j9z…",
  "type": "equipment",
  "position": { "x": 120, "y": 80 },
  "data": {
    "id": "eb-pq2220b",
    "category": "display",
    "name": "Projector",
    "model": "EB-PQ2220B",
    "manufacturer": "Epson",
    "description": "…",
    "inputs": [ … ], "outputs": [ … ], "bidirectional": [ … ],
    "imageUrl": "https://seoulav.github.io/AV-Portal/detail/images/eb-pq2220b-main.webp",
    "isReused": false,
    "portal": { "productId": "eb-pq2220b", "source": "portal", "detailUrl": "https://seoulav.github.io/AV-Portal/detail/?product=eb-pq2220b" }
  },
  "sourcePosition": "right",
  "targetPosition": "left"
}
```

**`data` 필드:**

| 필드 | 1.1 | 1.2 값의 출처 |
|---|---|---|
| `id` | 카탈로그 ID | **배치 단위 ID.** 보통은 Portal 제품 ID. TX/RX 쌍은 `<제품ID>:tx`·`<제품ID>:rx`, 시리즈 모델은 `<제품ID>:<모델 소문자>`(§6). `:`는 Portal ID에 쓰이지 않는 문자라 구분이 확실하다 |
| `category`, `name` | ✓ | §4 |
| `model` | ✓ | 상세 `model`. TX/RX 단위는 단위 모델명(예: `CT101-U`), 시리즈는 선택한 모델명 |
| `manufacturer` | ✓ | 목록 `brand`. RTCOM은 `RTCOM` |
| `description` | ✓ | 상세 `korean`(한글 한 줄 설명). 없으면 `english` |
| `series` | ✓ | 상세 `series`가 있으면 |
| `inputs`·`outputs`·`bidirectional` | ✓ | §3 단자. 방향별로 나눠 담는다 |
| `imageUrl` | ✓ | 목록 `card_image` → `https://seoulav.github.io/AV-Portal/detail/images/<파일>`. RTCOM은 `…/rtcom/images/<파일>`. 사진이 없으면 키를 뺀다 |
| `isReused` | ✓ | 사용자가 켠 값. **항상 넣는다**(기본 `false`) |
| `portal` | | `{productId, source: "portal"\|"rtcom", unit?: "tx"\|"rx", variant?, detailUrl}` |

- 노드 `id`는 `node_` + 소문자 ULID다. 1.1의 `node_<타임스탬프>`와 같은 접두어이고, 정렬하면 만든 순서가 된다.
- `sourcePosition`·`targetPosition`은 1.1 운영 파일 대부분에 있는 값이라 그대로 넣는다(`right`·`left`).

**메모·영역 노드:** 1.1 형식 그대로다(통합 기획 §6.1). `id` 접두어도 1.1과 같다(`annotation_`, `shape_`).

**저장하지 않는 키:** `measured`, `selected`, `dragging`, `dimmed`, `draggable`, 최상위 `width`/`height`, `quantity`, `selectedOptionQuantities`, `optionPortIds`, `selectedOptionIds`

### 8.3 엣지

```json
{
  "id": "e-node_01j9…-node_01j9…-01j9…",
  "type": "smoothstep",
  "source": "node_01j9…", "sourceHandle": "out-hdmi-1",
  "target": "node_01j9…", "targetHandle": "in-hdmi-2",
  "animated": false,
  "style": { "stroke": "#ef4444", "strokeWidth": 2 },
  "data": { "lineTypeId": "video", "signal": "HDMI", "label": "",
            "bomRows": [ { "cableType": "ready-made", "productName": "HDMI 케이블 3m", "lineTypeId": "video", "quantity": 1 } ] }
}
```

| 필드 | 1.1 | 1.2 |
|---|---|---|
| `id` | `e-<source>-<target>-<타임스탬프>` | 같은 형식, 끝을 ULID로 |
| `type` | `smoothstep` | 같다 |
| `source`·`sourceHandle`·`target`·`targetHandle` | ✓ | 같다. 양방향 단자 핸들은 `source_<단자ID>`/`target_<단자ID>` |
| `animated` | `false` | 같다 |
| `style` | `{stroke, strokeWidth}` | `stroke` = 선 종류 색, `strokeWidth` = 2 |
| `data.lineTypeId` | ✓ | 엣지 `signal`의 선 종류 |
| `data.label` | 있을 때만 | 같다 |
| `data.bomRows` | 있을 때만 | 같다. 1.1 형식 그대로(`cableType`·`productName`·`lineTypeId`·`length`·`quantity`) |
| `data.signal` | | 이 엣지가 나르는 표준 신호(§7.1) |

### 8.4 결정적 직렬화

- **노드 순서:** 영역(`shape`) → 장비 → 메모, 각 묶음 안에서 `id` 순. 영역이 장비 뒤에 그려지도록 앞에 둔다.
- **엣지 순서:** `id` 순
- **키 순서:** 이 문서의 예시 순서
- **좌표:** 소수 첫째 자리에서 반올림
- **형식:** 2칸 들여쓰기, UTF-8, LF, 끝 줄바꿈 1개

### 8.5 `issues[]`

```json
{ "code": "connector-adapter", "severity": "warning", "target": { "edge": "e-…" }, "detail": "HDMI → DVI" }
```

- `severity`는 `warning` 또는 `info`다. 오류는 저장을 막으므로 파일에 남지 않는다.
- `target`은 `{node}`·`{edge}`·`{node, port}` 중 하나다.
- 정렬은 `code`, `target` 순이다.
- 코드 목록은 통합 기획 §6.4의 코드와 이 문서 §7.1의 코드를 합친 것이다.

### 8.6 1.1 상위 집합 대조

1.1 운영 데이터(프리셋 6건 + 공유 5건)에서 **항상 있던 키**가 1.2에도 같은 위치·같은 타입으로 있는지 대조한다.

| 위치 | 1.1에서 항상 있던 키 | 1.2 |
|---|---|---|
| 최상위 | `version`, `nodes`, `edges`, `lineTypes`, `equipmentDB` | ✓ 모두 있음 |
| 장비 노드 | `id`, `type`, `position`, `data` | ✓ |
| 장비 `data` | `id`, `category`, `name`, `model`, `inputs`, `outputs`, `bidirectional` | ✓ |
| 단자 | `id`, `label`, `type`, `direction` | ✓ |
| 메모 노드 | `id`, `type`, `position`, `style`, `data` | ✓ |
| 엣지 | `id`, `type`, `source`, `sourceHandle`, `target`, `targetHandle`, `style`, `data` | ✓ |
| 엣지 `data` | `lineTypeId` | ✓ |

- 1.1에서 **가끔 있던 키**는 1.2에서 의미가 같을 때만 넣는다.
  - 넣는 것: `manufacturer`, `imageUrl`, `isReused`, `description`, `label`, `bomRows`, `sourcePosition`, `targetPosition`, `animated`
  - 빼는 것: `quantity`, 옵션 필드, 화면용 값(§8.2)
- P3 테스트는 1.1 가상 예시 파일(구 Builder 키 구조와 같음)과 1.2 예시를 이 표로 대조한다.

## 9. 상호작용 수치

구 Builder 실측 값:

- 단자 점: 8×8px
- 단자 행: 높이 24px, 행 간격 4px (반복 간격 28px)

"딱 점을 잡아야 해서 불편하다"는 지적은 이 수치와 맞는다.

| 항목 | 값 (초안) | 근거·조정 |
|---|---|---|
| 노드 폭·헤더·행 높이·행 간격 | 220 · 54 · 24 · 4 px | 구 Builder와 같다. 좌표 계산과 렌더링이 같은 상수 모듈을 쓴다 |

| 드래그 시작 거리 | 4px | 이보다 덜 움직이고 놓으면 클릭(단자 선택)으로 본다 |

| 범위 선택 | 장비는 사각형에 일부라도 걸리면 선택. 단자는 점 중심이 사각형 안에 있으면 선택 | React Flow `SelectionMode.Partial` + 단자 선택은 앱 상태 |
| 단자 선택 표시 | 단자 점에 2px 강조 테두리. 다중 선 긋기 중에는 커서 옆에 개수 배지 | P4 화면 시험에서 조정 |
| 화면 이동 | 가운데 버튼 드래그, Space + 왼쪽 드래그(C2) | `panOnDrag={[1]}` + Space 키 상태 |
| 확대·축소 | 휠. 최소 0.05, 최대 2 | 구 Builder 최소값 유지 |
| 다중 연결 대상 부족 | 연결 가능한 쌍만 연결, "N개 중 M개 연결" 알림(C1) | |

이 수치는 P4·P5의 브라우저 시험(통합 기획 §7.4)으로 확인하고, 바꾸면 이 표를 고친다.
