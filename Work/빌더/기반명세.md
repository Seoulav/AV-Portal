## 2. 표준 어휘와 변환 규칙

**적용 방식:** `beta/port-vocabulary.mjs`는 [부록 A](#부록-a-변환-규칙-원문)의 규칙을 **표의 순서대로** 적용한다. 앞에서 정해지면 뒤는 보지 않는다. 판단할 수 없는 행은 메우지 않고 "확인 필요"로 남긴다.

**한 행의 처리 순서:**

1. 단자가 아닌 행인지 본다(§2.1).
2. 커넥터를 정한다(§2.2). 다중 커넥터면 확인 필요.
3. 신호를 정한다(§2.3·§2.4).
4. 방향을 정한다(§2.5).
5. 수량을 정한다(§2.6).

### 2.1 단자가 아닌 행 (부록 A1)

| 순서 | 대상 칸 | 조건 | 분류 |
|---|---|---|---|
| 1 | availability | `미지원` | 미지원 |
| 2 | connector | `SERVICE`·`Reset`·`Security Lock`·`서비스 전용` | 서비스 |
| 3 | signal | `펌웨어`·`firmware`·`서비스 전용` (단 `재생`·`미디어`·`Storage`·`메모리`·`Viewer`가 있으면 제외) | 서비스 |
| 4 | connector | `무선`·`Wireless`·`Bluetooth`·`NFC`·`RFID`·`Wi-Fi`·`AirPlay`·`Google Cast`·`수신부` (단 `USB`가 있으면 제외) | 무선 |
| 5 | signal | `무선`으로 시작 | 무선 |
| 6 | connector + signal | `RF`와 `리모컨`이 함께 있음 | 무선 |
| 7 | connector | `슬롯`·`slot`·`보드(선택형)`·`CFexpress`·`카드` (단 `Combicon`·`온보드`·`USB`가 있으면 제외) | 슬롯 |
| 8 | condition | `모듈 칸`·`카드 구성에 따라`·`카드형` | 슬롯 |

동시 출력을 뜻하는 `(미러링)`은 무선이 아니다. 예: `HDMI 2.0 + 12G-SDI(미러링)`. 무선 미러링은 5번(`무선 미러링(…)`)이 잡는다.

### 2.2 커넥터 (형상이 적힌 경우만, 부록 A2)

- 기능만 적힌 칸(`Ethernet(LAN)`, `오디오 출력`, `IR 입력`)은 RJ45 등으로 **추정하지 않고** `UNKNOWN`으로 둔다. 커넥터를 몰라도 신호가 맞으면 연결할 수 있다(§7).
- 형상 이름이 없는 `9핀`, `headphone`, `스테레오 잭`도 `UNKNOWN`이다.

| 표준값 | 원문 예 |
|---|---|
| `UNKNOWN` | 칸 전체가 `정보 없음`·`MISSING`·`—`·`커넥터 규격 정보 없음`·빈칸. 또는 아래 어느 규칙에도 안 맞음 |
| `CAPTIVE` | `커넥터 없음(무단말 케이블 직결)`, `부착형 케이블` |
| `TERMINAL-BLOCK` | Phoenix, Combicon, Euro 3.8mm, 유로블록, 터미널 블록, Screw Terminal, 단자대, Barrier strip, WAGO |
| `BINDING-POST`, `SPEAKON`, `POWERCON` | Binding Post / Speakon·NL4 / powerCON |
| `IEC-C20`·`IEC-C14`·`IEC-C13`·`IEC` | C 번호가 적힌 IEC / 그 밖의 IEC·AC 인렛 |
| `SCHUKO`, `DC` | CEE7/7 / DC Jack·DC 입력 |
| `HD-BNC`, `BNC` | HD-BNC / BNC |
| `HDMI`, `DP`, `DVI` | HDMI / DisplayPort·DP / DVI |
| `DSUB-15`·`DSUB-25`·`DSUB-9` | D-sub 15·DB-15 / DB-25 / D-sub 9·DB-9 |
| `MINI-DIN-8`, `SFP`, `LC`, `SC` | Mini DIN 8 / SFP·SFP+ / LC·2LC / SC |

**다중 커넥터 → 확인 필요:** 다음 둘 중 하나에 해당하면 다중 커넥터로 본다.

1. 한 칸에서 서로 다른 커넥터 계열(부록 A2의 계열 표)이 2개 이상 나온다.
2. `또는`·`or`·`및`·`+`·`,`로 나눈 조각 가운데 커넥터 계열이 든 조각이 2개 이상이다.

예외도 있다.

| 표기 | 처리 | 이유 |
|---|---|---|
| `Combo` | 다중 아님 | 콤보 잭 하나 |
| `브레이크아웃` | 다중 아님 | 본체 단자 하나 + 분기 케이블 |
| `RJ-45(RS-232 배선)` | RJ45 하나 | 배선 설명이다 |
| `SDI (BNC)` | BNC 하나 | 신호 이름과 커넥터를 함께 적은 것이다 |

다중 커넥터 예:
- `HDMI 1.4 또는 3G-SDI`
- `HDMI 2.0 + 12G-SDI(미러링)`
- `USB Type-C / RJ45-DB9`
- `XLR ×1, 1/4"(6.35 mm) ×1`
- `1/4" (6.35 mm) 및 XLR`
- `3-pin XLR 또는 5-pin XLR`

### 2.3 신호 (부록 A3)

**찾는 순서**

1. `signal` 칸에서 찾는다.
2. 하나도 없으면 `connector` 칸에서 찾는다.
3. `protocol` 칸에서는 `DANTE`·`AES67`·`COBRANET`·`POE`만 **덧붙인다**. 조건은 이미 대칭 신호가 있거나 커넥터가 `RJ45`·`SFP`인 경우다.
   - `ETHERNET`·`HDBASET`은 protocol 칸에서 붙이지 않는다. DIGITAL LINK 행에 `100Base-TX`가 적혀 있어도 이더넷 단자가 되지 않는다.
4. signal 또는 protocol에 `독자`·`proprietary`·`전용 프로토콜`이 있으면 `ETHERNET`·`POE`를 뺀다. 회의 시스템 독자 버스는 이더넷 스위치에 꽂는 단자가 아니다.
5. 그래도 없으면 커넥터가 신호를 정의하는 경우만 채운다.
   - `HDMI`→`HDMI`, `DP`→`DP`, `DVI`→`DVI`, `SPEAKON`→`SPEAKER`, `USB*`→`USB`
6. 그래도 없고 광 커넥터(`SFP`·`LC`·`SC`)이거나 `Fiber`·`광섬유` 등이 적혀 있으면 `FIBER`. **`FIBER`는 다른 신호가 하나도 없을 때만** 붙는다. 광 이더넷 SFP는 `ETHERNET`이 되고, 광 연장기의 전용 광 링크만 `FIBER`가 된다.

`group` 칸은 쓰지 않는다. 예를 들어 "Audio Network" 같은 묶음 이름이 아날로그 단자에 네트워크 신호를 잘못 붙인다.

**표준 신호 (표 순서 = 주 신호 우선순위)**

| 표준 신호 | 표시명 | 원문 근거 (요약) | 붙이지 않는 경우 |
|---|---|---|---|
| `POWER` | Power | 전원 계열 커넥터, `Mains`·`AC power`·`DC power`·`전원 입력`·`DC IN` 등 | `팬텀`·`phantom`·`PoE`가 signal 또는 connector 칸에 있음 |
| `BLU-LINK` | BLU link | `BLU link` | |
| `DANTE` · `AES67` · `COBRANET` | Dante · AES67 · CobraNet | 각 이름 | |
| `AVB` | AVB | (이번 데이터에 없음. 표준값으로만 둔다) | |
| `HDBASET` | HDBaseT | `HDBaseT`, `HDBT`, `DIGITAL LINK` | |
| `HDMI` · `DVI` · `DP` · `SDI` | HDMI · DVI · DP · SDI | `HDMI`·`TMDS` / `DVI` / `DisplayPort`·`DP` / `SDI` | `DP`·`SDI`는 대문자 단어만 |

### 2.4 신호 후처리

| 순서 | 처리 |
|---|---|
| 1 | `DANTE`·`AES67`·`COBRANET`·`AVB`·`POE`가 있으면 `ETHERNET`을 덧붙인다. 일반 네트워크 스위치와 연결하기 위해서다. `BLU-LINK`·`HDBASET`에는 붙이지 않는다 |
| 2 | 신호를 위 표 순서로 정렬한다. 첫 번째가 **주 신호**다 |
| 3 | 주 신호가 `POWER`이고 `USB`가 있으면 `USB`를 앞으로 옮긴다. USB 전원 출력 단자가 전원 단자로 숨지 않게 하기 위해서다 |
| 4 | signal 칸에 `또는`·`or`가 있고 신호 계열(대칭 신호는 한 계열)이 둘 이상이면 확인 필요. `멀티뷰어` 출력도 확인 필요 |

### 2.5 방향 (부록 A4)

| 원문 | 표준값 |
|---|---|
| `IN`, `입력` | `in` |
| `OUT`, `출력` | `out` |
| `IN/OUT`, `I/O`, `BIDIR`, `양방향` | `both` |
| 그 밖(빈칸·`N/A`·`정보 없음`·`IN/LOOP`) | 확인 필요 |

**대칭 신호 정규화:** 단자의 신호가 **모두** 대칭 신호(`ETHERNET`·`DANTE`·`AES67`·`AVB`·`COBRANET`·`POE`)이면, 원문 방향과 관계없이 `both`로 둔다. 원문 방향이 빈칸·`N/A`여도 마찬가지다.

- 이더넷 단자는 실물에 방향이 없다. 디스플레이 LAN이 `IN`으로 적혀 있어도 신호는 양방향이다. 이것은 추정이 아니라 신호의 정의다.
- 이렇게 하면 LAN끼리 직접 연결해도 엣지의 출발 핸들이 항상 출발 가능한 단자를 가리킨다(§7·§8.3). 1.1의 양방향 핸들 규칙(`source_`/`target_`)도 그대로 쓸 수 있다.
- `BLU-LINK`·`HDBASET`은 대칭 신호가 아니다. IN/OUT 방향을 지킨다.

## 3. 단자 ID와 이름

### 3.1 ID 형식

```
<direction>-<신호키>-<n>
```

| 부분 | 값 | 예 |
|---|---|---|
| `direction` | `in` · `out` · `both` (1.1 형식과 같음) | |
| `신호키` | 주 신호의 소문자 키(영숫자·하이픈) | `hdmi`, `sdi`, `dante`, `line-audio`, `rs-232` |
| `n` | 같은 배치 단위 안에서 같은 `direction`·`신호키`끼리 1부터 매기는 번호 | `in-hdmi-1`, `in-hdmi-2`, `out-hdmi-1` |

- 한 배치 단위(노드) 안에서 유일하다. 1.1과 같다.
- 공백·특수문자를 쓰지 않는다. 구 데이터의 `out-hdmi out-1` 같은 오류를 막는다.

### 3.2 번호 매기는 순서

1. 상세 JSON `io[]`의 **행 순서**를 따른다.
2. 한 행에서 N개가 나오면 연속으로 매긴다.
3. 같은 방향·신호키가 여러 행에 나뉘면 앞 행부터 이어서 매긴다.
4. **TX/RX로 나눈 제품(§6.1)은 단위마다 1부터 다시 매긴다.** 예: CT101-U와 CR101-U의 RS-232는 둘 다 `both-rs-232-1`

Portal에서 행 순서나 수량을 고치면 번호가 바뀔 수 있다.

- 이미 저장한 구성도는 노드가 배치 당시 단자를 품고 있어 계속 열린다.
- 차이는 `library-drift` 이슈로 알린다.
- P5에서 "현재 라이브러리로 단자 다시 맞추기" 도구를 둔다.

### 3.3 이름 (`label`)

**기본 이름:** `<표시명> <In|Out|I/O> <n>`

- 예: `HDMI In 1`, `Dante I/O 1`, `Line Audio Out 2`
- 1.1 운영 데이터("SDI Out 1", "LAN 1")와 같은 모양이다.

**그룹 구분:** 같은 방향·신호키의 단자가 **서로 다른 `group`**에서 나오면 원문 `group`을 괄호로 붙인다.

- 예: `HDMI In 1 (Front)`
- TX/RX 단위에서는 `TX · `·`RX · ` 접두어를 뗀 뒤의 `group`을 쓴다.

**Port Map 이름:** P2 이후 `beta/builder-port-links.mjs`에 대응을 적은 제품은 Port Map의 `label`을 쓴다.

- 예: `HDMI 1 입력`
- 대응표 형식: `{ "<배치 단위 ID>": { "in-hdmi-1": 1, "in-hdmi-2": 2 } }` (단자 ID → Port Map 번호 `n`)
- 사람이 사진과 I/O 행을 보고 채운다. 이름이 비슷하다고 자동으로 짝짓지 않는다.

### 3.4 단자 객체 (1.2)

```json
{ "id": "out-hdmi-1", "label": "HDMI Out 1", "type": "video", "direction": "out",
  "connector": "HDMI", "signals": ["HDMI"], "verification": "FOUND",
  "portalIo": { "group": "Output", "connector": "HDMI Type-A", "signal": "HDMI 2.0 out (Scaler/Bypass)" } }
```

| 필드 | 1.1에 있음 | 뜻 |
|---|---|---|
| `id`, `label`, `type`, `direction` | ✓ | 1.1과 같다. `type`은 선 종류 ID(§5) |
| `connector` | | 표준 커넥터(§2.2) |
| `signals` | | 표준 신호 목록(§2.3). 첫 번째가 주 신호 |
| `verification` | | 원본 I/O 행의 검증 상태 그대로 |
| `portalIo` | | 원본 I/O 행의 `group`·`connector`·`signal` 원문. 사람이 근거를 찾아가는 용도. 노드의 `data.portal`과 이름이 겹치지 않게 했다 |

키 순서는 위 예시 순서다.

## 6. TX/RX 쌍과 시리즈 제품

### 6.1 TX/RX로 나누는 제품 (10종)

다음 RTCOM 제품은 **모든** I/O 행의 `group`이 `TX · …` 또는 `RX · …`로 시작한다. 이 접두어로 배치 단위 2개를 만든다.

| 제품 ID | 원래 `model` | TX 단위 | RX 단위 |
|---|---|---|---|
| `rtcom-ct101-u-cr101-u` | CT101-U / CR101-U | CT101-U | CR101-U |
| `rtcom-ct103-u-h-cr103-u` | CT103-U-H / CR103-U | CT103-U-H | CR103-U |
| `rtcom-ct104-u-cr104-u` | CT104-U / CR104-U | CT104-U | CR104-U |
| `rtcom-ft101-u-fr101-u` | FT101-U / FR101-U | FT101-U | FR101-U |
| `rtcom-ft103-u-h-fr103-u` | FT103-U-H / FR103-U | FT103-U-H | FR103-U |
| `rtcom-xdm-ct103-cr103` | XDM-CT103 / XDM-CR103 | XDM-CT103 | XDM-CR103 |
| `rtcom-xdm-ft101-fr101` | XDM-FT101 / XDM-FR101 | XDM-FT101 | XDM-FR101 |
| `rtcom-spx-rx-tx` | SPX-TX / SPX-RX | SPX-TX | SPX-RX |
| `rtcom-obhd-2c` | OBHD-2C | OBHD-2C (TX) | OBHD-2C (RX) |
| `rtcom-obux-1c` | OBUX-1C | OBUX-1C (TX) | OBUX-1C (RX) |

**단위 모델명**

- `model`에 ` / `가 있으면 `TX`·`RX` 순서로 짝짓는다. 단, `rtcom-spx-rx-tx`는 원문 순서가 `SPX-TX / SPX-RX`라 그대로 맞는다.
- 모든 TX 행의 `condition` 첫 조각(`·` 앞)이 **한 모델명**이고, RX 행도 마찬가지이며, 두 이름이 `model`의 두 조각과 같아야 한다. 위 8종은 모두 이 조건을 만족한다. `model`에 ` / `가 없는 2종은 첫 조각이 `TX`·`RX`여야 한다.
- ` / `가 없으면 `<model> (TX)`·`<model> (RX)`로 둔다.

**그 밖의 규칙**

- **배치 단위 ID:** `<제품ID>:tx`, `<제품ID>:rx`. 노드 `data.portal.unit`은 `tx`·`rx`다.
- **단자:** 단위마다 따로 번호를 매긴다(§3.2). 이름은 접두어를 뗀 `group`으로 만든다.
- **사이드바:** 제품 하나 아래 TX·RX 두 항목으로 보인다.
- **분리 조건:** I/O 행 접두어가 **전 행에 빠짐없이** 있고 위 모델명 조건을 만족할 때만 나눈다. 일부 행에만 있거나 모델명이 맞지 않으면 TX·RX를 한 노드에 섞지 않는다. 단자 없이 한 단위로 두고, 모든 행을 확인 필요(사유 `txrx`)로, 제품 이슈 `txrx-unresolved`로 남긴다. 생성기는 실패하지 않는다. 판정은 시리즈(§6.3)가 아닌 제품에만 한다.

### 6.2 나누지 않고 보류하는 제품

| 제품 ID | 처리 |
|---|---|
| `rtcom-xdm-ctr100`, `rtcom-xdm-ctr100-pse` | 한 대가 설정에 따라 TX도 되고 RX도 된다. 1단계에서는 한 단위로 두고, 전송 단자는 원문 방향대로 둔다. 모드 선택 UI는 제품 결정이 필요하다(E6) |
| `rtcom-spx-r6` | TX·RX 모듈을 칸마다 꽂는 랙 프레임이다. 모듈 칸 행은 슬롯으로 분류된다(§2.1). IR·전원 단자만 생긴다. 카드 구성과 함께 P9에서 다룬다 |

일반 제품에서도 `TX`·`RX`라는 말이 나오는 36건을 확인했다. 모두 RS-232 핀 이름(Tx·Rx)이나 전원 조건 설명이라 배치 단위를 나눌 대상이 아니다.

### 6.3 시리즈 제품

- `rtcom-xdm`·`rtcom-spx`·`rtcom-vdm`은 `itemType: SERIES`이고 **I/O 행이 0개**다.
- `lineup`에 모델·카드·전송기·전원이 섞여 있다.

| 시리즈 | lineup | 메인프레임 |
|---|---|---|
| XDM | 26 | 7 (XDM-12 … XDM-288) |
| SPX | 10 | 5 (SPX-M810 … SPX-M24120) |
| VDM | 25 | 10 (VDM-8X … VDM-288X) |

**1단계 처리**

- 시리즈를 배치하면 `lineup` 중 **`kind: 메인프레임`인 모델만** 고르게 한다.
  - 카드·전송기·전원은 고를 수 없다. 전송기는 이미 별도 제품(§6.1)이고, 카드는 P9에서 다룬다.
- 배치 단위 ID는 `<제품ID>:<모델 슬러그>`다. 슬러그는 모델명을 소문자로 바꾸고 영숫자 외 문자를 `-`로 바꾼 것이다. 예: `rtcom-xdm:xdm-12`, `rtcom-spx:spx-m810` 슬러그가 겹치면 두 번째부터 `-2`·`-3`을 붙이고 제품 이슈 `variant-slug-duplicate`를 남긴다. 모델의 `description`은 lineup의 모델별 `summary`이고, 없으면 시리즈 설명이다. 시리즈에 I/O 행이 생기면 어느 모델의 단자인지 알 수 없으므로 모든 행을 확인 필요(사유 `series-io`)로 둔다.
- 노드 `data.portal.variant`에 원래 모델명(`XDM-12`)을 둔다.
- 노드는 **단자 없이** `no-ports`·`series-config-pending` 이슈와 함께 놓인다.
- 매트릭스를 결선하려면 RTCOM 원본(`rtcom-configurator`)에 프레임·카드 단위 I/O가 먼저 있어야 한다. RTCOM 원본은 Portal에서 고치지 않는다(AGENTS.md).

## 7. 연결 규칙

### 7.1 판정표

"출발"은 사용자가 선을 끌기 시작한 단자, "도착"은 놓은 단자다.

- 판정은 아래 순서로 처음 걸리는 **차단**에서 멈춘다.
- 차단이 없으면 해당하는 경고·안내를 모두 붙인다.

| 순서 | 처리·조건 | 판정 | 이슈 코드 |
|---|---|---|---|
| 0 | 출발이 `in`이고 도착이 `out`·`both`이면, 또는 출발이 `both`이고 도착이 `out`이면 **출발과 도착을 바꾼다** | — | — |
| 1 | 출발 또는 도착 단자에 이미 엣지가 있다 | **차단** | `port-occupied` |
| 2 | 같은 노드의 단자끼리 | **차단** | `self-loop` |
| 3 | 공통 신호가 없고 §7.2 레벨 차이 쌍도 아니다 | **차단** | `signal-mismatch` |
| 4 | 방향이 `in→in` 또는 `out→out`이다 | **차단** | `direction` |
| 5 | 연결 신호가 `POWER`이고 전원 결선이 꺼져 있다 | **차단** | `power-disabled` |
| 6 | 커넥터가 다르다(§2.8 호환 묶음은 같은 것으로 본다) | 경고 | `connector-adapter` |
| 7 | 어느 쪽 커넥터가 `UNKNOWN`·`CAPTIVE`다 | 안내 | `connector-unknown` |
| 8 | 연결 신호가 §7.2 레벨 차이 쌍이다 | 경고 | `signal-level` |
| 9 | 어느 단자의 검증 상태가 `VERIFIED`·`FOUND`가 아니다 | 경고 | `unverified-port` |

**방향**

- 0번을 거친 뒤 허용되는 조합: `out→in`, `out→both`, `both→in`, `both→both`
- 사용자는 어느 쪽에서 선을 그어도 된다. 저장된 엣지의 `source`는 항상 신호를 내보내는 쪽(또는 양방향 단자)이다.
- 이더넷 계열 단자는 §2.5에서 이미 `both`로 정규화됐다. 그래서 LAN끼리 직접 연결해도 4번에 걸리지 않는다.

**연결 신호 (`data.signal`)**

- 공통 신호 중 **0번을 거친 뒤의 source**(신호를 내보내는 쪽) 단자의 `signals` 순서에서 가장 앞선 것이다.
- 레벨 차이 쌍으로 연결된 경우는 0번을 거친 뒤의 source 쪽 신호다.

### 7.2 레벨 차이 쌍

| 쌍 | 이유 |
|---|---|
| `LINE-AUDIO` ↔ `MIC-AUDIO` | 실제로 자주 연결하지만 레벨 설정이 필요하다 |

이 표에 없는 서로 다른 신호끼리는 연결할 수 없다(3번).

**장비 노드 최상위 키**

순서는 `id`, `type: "equipment"`, `position`, `data`, `measured`, `sourcePosition: "right"`, `targetPosition: "left"`다.

- `id`는 `node_` + 소문자 ULID다. 1.1의 `node_<타임스탬프>`와 접두어가 같고, 정렬하면 만든 순서가 된다.
- `measured`는 `{width: 220, height: <계산값>}`이다. 높이는 `builder/engine/geometry.mjs`의 `nodeHeight`이며 구 Builder `calculateNodeHeight`와 같은 식이다.
  - `max(100, 12 + 54 + (사진이 있으면 68) + 단자 높이 + 12)`
  - 단자 높이: 입력·출력 중 많은 쪽 N행이면 `N×28−4`. 양방향 B행이 함께 있으면 `+ 8 + 13 + (B×28−4)`. 양방향만 있으면 `B×28−4+13`
  - 구 Builder는 사진이 없을 때도 분류별 기본 그림을 넣어 거의 항상 68을 더했다. 새 Builder는 `imageUrl`이 있을 때만 더한다
  - 1.1 파일 대부분에 있던 키다(장비 노드 152개 중 129개).
  - 데이터만으로 정해지는 값이라 저장해도 결정적이다.

**메모·영역 노드**

- 1.1 형식 그대로다(통합 기획 §6.1).
- `id` 접두어도 1.1과 같다(`annotation_`, `shape_`).
- `measured`는 `style`의 폭·높이와 같게 넣는다.

**저장하지 않는 키**

- 화면 상태: `selected`, `dragging`, `dimmed`, `draggable`
- 최상위 `width`/`height`
- 취소·보류된 기능: `quantity`, `selectedOptionQuantities`, `optionPortIds`, `selectedOptionIds`

`data` 키 순서는 `lineTypeId`, `signal`, `label`, `bomRows`다.

### 8.4 결정적 직렬화

- **노드 순서:** 영역(`shape`) → 장비 → 메모. 각 묶음 안에서는 `id` 순이다. 영역이 장비 뒤에 그려지도록 앞에 둔다.
- **엣지 순서:** `id` 순
- **키 순서:** §3.4·§8.1~§8.3과 부록 C의 순서
- **좌표·크기:** 0.1 단위로 반올림(소수 첫째 자리까지 남긴다)
- **형식:** 2칸 들여쓰기, UTF-8, LF, 끝 줄바꿈 1개
- **모르는 키:** 이 문서에 없는 키는 직렬화할 때 버린다. 화면 상태(`selected`·`dragging`·`dimmed` 등)가 저장되지 않게 하기 위해서다
- **구현:** `builder/engine/serialize.mjs`(`normalizeDiagram`·`serializeDiagram`). 저장된 예제를 다시 직렬화하면 같은 바이트가 나오는지 테스트한다

### 8.5 `issues[]`

```json
{ "code": "connector-adapter", "severity": "warning", "target": { "edge": "e-…" }, "detail": "HDMI → DVI" }
```

| 코드 | 심각도 | 대상 |
|---|---|---|
| `connector-adapter`, `signal-level`, `unverified-port` | warning | edge |
| `connector-unknown` | info | edge |
| `no-ports`, `series-config-pending`, `product-removed` | warning | node |
| `library-drift` | info | node |
| `cable-unspecified` | info | edge |

- 오류(차단 사유)는 저장 자체를 막으므로 파일에 남지 않는다.
- `target`은 `{node}`·`{edge}`·`{node, port}` 중 하나다.
- 정렬 순서: `code` → `target`의 `node`·`edge`·`port` 값(문자열) → `detail`

```js

//      커넥터가 TERMINAL-BLOCK·XLR·XLR-COMBO·BINDING-POST이고 커넥터 칸에 '공용'이 없으면 N

// 3) /^([1-9]\d*)\s*[x×]\s*\S/ → N
// 4) 수량 칸이 비었고 커넥터 칸의 개수가 있으면 그 수

```

### A6. 확인 필요 사유 순서

`multi-connector` → `multi-signal` → `no-signal` → `direction` → `quantity`. 다중 커넥터면 신호·수량은 보지 않는다. 제품 단위 사유: `txrx`(TX/RX 분리 근거 부족, §6.1), `series-io`(시리즈에 생긴 I/O 행, §6.3).
