## 목표

**지금:** [기반 명세](../기반명세.md)는 Portal I/O를 단자로 바꾸는 규칙(부록 A)과 측정 결과(§1.4)를 문서로만 갖고 있다. 측정에 쓴 스크립트는 저장소 밖에 있다.

**이 작업이 끝나면:**

- 저장소 안의 생성기가 Portal 데이터에서 `builder-library.json`을 만든다.
- 이 파일은 Builder 앱(P4)과 검증기(P3)가 읽을 유일한 장비 라이브러리다.
- 같은 데이터로 기반 명세 §1.4의 수치를 그대로 재현한다.
- 화면은 없다.

## 범위

### 할 것

1. **`beta/port-vocabulary.mjs`** — 기반 명세 부록 A를 그대로 옮긴 규칙 표와 어휘
   - A1 단자가 아닌 행, A2 커넥터와 다중 커넥터 검사, A3 신호와 후처리, A4 방향, A5 수량, A6 확인 필요 사유 순서
   - 표준 신호 목록: 표시명, 선 종류, 대칭 여부
   - 표준 커넥터 목록, 호환 묶음(§2.8), 레벨 차이 쌍(§7.2)
   - 선 종류 12종: 기존 7종 + `speaker`·`fiber`·`analog-video`·`rf` + 예약 `power`
   - 개별 지정 표(제품 ID + `io` 행 위치 → 결과). **빈 표로 시작한다.** 채우는 일은 P6이다
   - `VOCABULARY_VERSION = "1.0.0"`
2. **`beta/builder-library.mjs`** — 화면과 무관한 순수 함수
   - I/O 행 분류
   - 제품 → 배치 단위: 일반 제품, TX/RX 10종(§6.1), 시리즈 메인프레임(§6.3)
   - 단자 ID·번호·이름(§3), 카테고리 대응(§4), 단자 `type`(§5.3)
   - 1.1 `Equipment` 객체 조립(§8.2 `data` 필드와 순서)
   - 제품별 준비도: 단자 수, 확인 필요 행, 단자가 아닌 행
3. **`beta/build-builder-library.mjs`** — 명령
   - `--out <경로>`: 결과 파일 위치. 기본값은 `beta/.generated/builder-library.json`
   - `--report`: 요약 표를 화면에 출력. 형식은 §1.4와 같은 분류·제품 수, 사유별·제조사별 확인 필요 행 수
   - 출력은 결정적이다. 제품은 ID 순이고, 2칸 들여쓰기, LF, 끝 줄바꿈 1개
4. **라이브러리 JSON 형식** (`schema: "av-portal.builder-library"`, `schemaVersion: "1.0.0"`)
   - `source`: `catalogSha`·`detailSetSha`·`rtcomSha`·`vocabularyVersion`. 각 SHA-256 계산 방법을 코드 주석과 명세에 적는다
   - `lineTypes`: 선 종류 12종
   - `vocabulary`: 신호·커넥터·호환 묶음·레벨 차이 쌍
     - P3 검증기와 P4 앱은 이 값을 읽는다. `beta/` 모듈을 직접 가져오지 않는다
   - `products[]`: 제품마다 다음 필드를 둔다
     - `productId`·`source`·`brand`·`product`·`categories`·`detailUrl`·`imageUrl`
     - `placeable`: §4.3에서 빼는 분류면 `false`
     - `units[]`: `unitId`·`unit?`·`variant?`·`equipment`(1.1 `Equipment` 모양)
     - `unresolved[]`: `ioIndex`·`group`·`connector`·`signal`·`reason`
     - `nonPort[]`: `ioIndex`·`kind`
     - `readiness`
5. **테스트 `tests/builder-library.test.mjs`**
   - **규칙 단위 시험:** 부록 A의 규칙 행마다 실제 원문 사례를 1개 이상 둔다
   - **리뷰 회귀 사례:**
     - mezzo 공용 RJ45 `4채널` → 확인 필요
     - comtech `AUX` 제어 → GPIO만
     - DIGITAL LINK + `100Base-TX` → HDBASET만
     - Plixus 독자 버스 → 확인 필요
     - 광 연장기 LC → FIBER, 스위치 SFP → ETHERNET
     - `(미러링)` → 다중 커넥터
     - 카드형 → 슬롯
     - `Security Lock Slot` → 서비스
     - `DC IN XLR 4핀` → XLR4
   - **배치 단위:**
     - TX/RX 10종의 단위 모델명이 `condition`과 맞는지
     - 시리즈 메인프레임이 22개인지
     - 단위별 단자 번호가 1부터 시작하는지
   - **형식:**
     - 단자 ID가 형식에 맞고 노드 안에서 유일한지
     - 1.1 `Equipment` 필수 키가 있는지
     - 공개 차단 문자열(`verify-pages.mjs:316`)이 없는지
   - **결정성:** 두 번 생성한 바이트가 같은지
   - **현재 데이터 고정 수치는 테스트에 넣지 않는다.** Portal 데이터가 보강되면 수치가 달라지는 것이 정상이기 때문이다. 기준 커밋 재현은 완료 조건에서 한 번 확인한다
6. **배포 연결 (결정 D-a 기본값)**
   - `.github/workflows/pages.yml`에서 `npm test` 다음에 `node beta/build-builder-library.mjs --out beta/site/builder-library.json --report`를 실행한다
   - 공개 주소는 `https://seoulav.github.io/AV-Portal/builder-library.json`이다
   - 이 파일은 저장소에 **커밋하지 않는다.** `.gitignore`에 `beta/.generated/`와 `beta/site/builder-library.json`을 넣는다
   - `verify-pages.mjs`의 최상위 파일 목록은 바꾸지 않는다. 생성 단계가 검사 뒤에 오기 때문이다
7. **문서**
   - 기반 명세 머리말과 통합 기획 §4.5·§9의 "커밋 + `--check`" 문장을 D-a 결정으로 고친다

## 결정이 필요한 사항

| ID | 항목 | 기본값 | 이유 |
|---|---|---|---|
| D-a | 생성 결과를 저장소에 커밋할지 | **커밋하지 않고 배포할 때 만든다** | 아래 참고 |
| D-b | P2부터 공개 주소로 내보낼지 | 내보낸다 | 견적 담당자가 단자 데이터 모양을 미리 볼 수 있다. 공개 데이터에서 파생한 것이라 새로 노출되는 정보가 없다 |

**D-a를 커밋하지 않는 쪽으로 정한 이유**

검색 인덱스처럼 커밋하고 `--check`로 고정하면 두 가지 문제가 생긴다.

- 모든 Portal 데이터 PR(Codex 작업 포함)과 RTCOM 자동 동기화 워크플로가 매번 라이브러리를 다시 만들어야 한다. 하지 않으면 배포가 실패한다.
- 그러려면 AGENTS.md와 `sync-rtcom.yml`을 바꿔 다른 작업 흐름에 의무를 지워야 한다.

반면 커밋해서 얻는 이점(PR diff로 단자 변화를 보는 것)은 Builder 앱이 없는 지금은 작다. 대신 배포 로그에 `--report` 요약을 남긴다.

이 결정은 다음 문장을 바꾼다.

- 기반 명세 머리말의 "P2 생성기가 결과를 `--check`로 고정"
- 통합 기획 §4.5의 "`beta/site/`에 커밋"
