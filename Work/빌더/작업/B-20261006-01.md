## 범위

**할 것:**

1. **I/O 표기 빈도 분석.** 대상은 상세 260건과 RTCOM 32건의 `io[]` 전체 1,404행이다. connector·signal·direction·quantity·availability 값별 빈도를 세고, 상위 몇 개 표기가 전체 행의 몇 %를 덮는지 기록한다.
2. **표준 어휘 확정.** connector·signal 표준값 목록을 확정한다. 원래 표기 → 표준값 대응표 초안을 상위 빈도부터 만들고, 덮는 비율을 적는다. 판단이 애매한 표기는 "확인 필요" 목록으로 따로 둔다.
3. **단자 ID·이름 규칙.** `${direction}-${신호키}-${n}`의 신호키 목록, 번호 매기는 순서, 여러 행이 같은 신호·방향일 때의 처리, Port Map 이름 대응표 형식을 정한다.
4. **카테고리 대응.** Portal 2단계(L1) → 1.1 `category`, 3단계(L2) → `name`. 상세 8건의 2단계 카테고리 처리를 정한다.
5. **선 종류 대응.** 기존 `lineTypeId` 7종과 표준 신호의 대응, 신규 ID(`speaker`·`fiber`·`analog-video`, 예약 `power`)와 색을 정한다.
6. **TX/RX 분리 규칙.** RTCOM 연장기 15건과 일체형·분배기 10건의 `group`/`condition`을 조사해 분리 근거가 명확한 제품과 모호한 제품을 나눈다.
7. **연결 규칙 표 확정.** 통합 기획 §5를 판정표(허용·경고·차단 × 조건)로 확정하고, 테스트 사례 목록을 만든다.
8. **1.2 호환 명세 확정.** 통합 기획 §6.2의 유지·채움·추가·제외 표를 필드 단위로 확정한다. 1.1 가상 예시와 1.2 가상 예시를 문서에 넣는다.
9. **상호작용 수치.** 근접 연결 반경(시작 16px, 끝 40px 초안), 단자 행 높이, 선택 표시 방식을 정한다. 화면 시험으로 조정하는 일은 P4에서 한다.

**하지 않을 것:**

- 코드, 생성기, Portal 데이터 수정. 분석 스크립트는 저장소 밖 임시 폴더에서 돌리고 결과 수치만 문서에 적는다.
- 대응표의 **파일**(`beta/port-vocabulary.mjs`) 작성. 이것은 P2에서 이 문서의 표를 옮겨 만든다.

**지킬 결정 (통합 기획 §0):**

- Portal 제품만 쓴다.
- 1.1 형식 호환, 필드는 추가만 한다.
- 노드 1개 = 1대, 단자 1개 = 연결 1개.
- 출력 분배는 차단한다.
- 전원 확장 자리를 남긴다.
- 제조사 사양을 추측하지 않는다. 대응표에 없는 표기는 "확인 필요"로 남긴다.
