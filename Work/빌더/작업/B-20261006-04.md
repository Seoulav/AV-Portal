## 목표

**지금:** 장비 라이브러리(공개 주소)와 구성도 엔진(`builder/engine/`)은 있지만 화면이 없다.

**이 작업이 끝나면:** `https://seoulav.github.io/AV-Portal/builder/`에서 다음을 할 수 있다.

1. Portal 장비를 검색해 캔버스에 놓는다.
2. 단자끼리 선을 긋는다. 연결 가능 여부는 엔진의 §7 규칙으로 정한다.
3. 케이블 정보(`bomRows`)를 넣는다.
4. 구성도 JSON 1.2로 내보내고 다시 연다.
5. 작업은 브라우저에 자동 저장된다.

**아직 하지 않는 것:** 근접 연결·범위 선택·가운데 버튼 이동·평행선 일괄 연결 같은 편집 조작은 B-05와 P5에서 한다. 이번에는 React Flow 기본 조작(단자 점을 잡아 연결, 드래그로 이동)을 그대로 쓴다.

## 범위

### 할 것

1. **`builder/` 앱 설정**
   - `package.json`·`package-lock.json`: React 19, `@xyflow/react` 12, zustand 5, Vite, TypeScript
   - 개발 의존성: vitest, ajv
   - 루트 `package.json`의 의존성 0개는 그대로 둔다. npm 의존성은 `builder/` 안에만 둔다
   - Vite `base`는 `/AV-Portal/builder/`로 두고 소스맵은 배포하지 않는다
2. **화면**: 구 Builder의 배치를 따르되 Portal의 밝은 스타일(흰 바탕·파란 강조, UI_UX_SPEC §252)을 쓴다
   - **장비 목록(왼쪽)**
     - 공개 `builder-library.json`(같은 출처의 `../builder-library.json`)을 읽는다
     - 카테고리·제조사 묶음과 검색을 둔다. TX/RX·시리즈 모델은 단위별 항목으로 보인다
     - `placeable: false` 제품은 숨긴다
     - 단자가 없거나 확인 필요 행이 있는 제품은 배지로 표시한다
   - **캔버스**
     - 장비를 끌어다 놓는다. 노드는 엔진 `geometry.mjs`의 치수와 1.1 핸들 규칙(`source_`/`target_`)으로 그린다
     - 단자는 신호 색으로 칠하고, 단자 이름과 검증 상태 배지를 단다
     - React Flow `isValidConnection`과 `onConnect`에 엔진 `judgeConnection`·`connectPorts`를 연결한다. 막히는 연결은 이유(방향, 신호 불일치, 이미 사용 중 등)를 짧게 알린다
     - 메모·영역 노드는 구 Builder 기본값으로 둔다
   - **엣지 편집 패널**: 엣지를 선택하면 라벨과 케이블(`bomRows`: 기성·제작, 제품명, 길이·수량)을 편집한다
   - **상단 막대**
     - 새 구성도, 열기(JSON 파일), 내보내기(JSON 1.2, 엔진 `serializeDiagram`)
     - Undo/Redo(최근 50단계, 구 Builder와 같다)
   - **자동 저장**: localStorage 키 `av-portal-builder:current`
     - 같은 출처(`seoulav.github.io`)의 다른 앱과 겹치지 않게 접두어를 둔다
     - 열 때 엔진 `validateDiagram`으로 검사하고, 오류가 있으면 불러오지 않고 알린다
3. **엔진 연결**: 앱은 `builder/engine/*.mjs`를 그대로 import한다. 규칙을 앱에 따로 두지 않는다
4. **빌드·배포**
   - `.github/workflows/pages.yml`: 기존 단계와 라이브러리 생성 뒤에 `builder/`에서 `npm ci && npm run build`를 하고, 결과를 `beta/site/builder/`에 복사해 함께 올린다. `verify-pages`의 최상위 목록 검사보다 뒤라 충돌하지 않는다
   - `.github/workflows/builder-ci.yml`(PR, `builder/`·`beta/`·`tests/` 변경 시): 타입 검사, vitest, ajv 스키마 검증(F-b), 빌드
   - `.gitignore`: `builder/node_modules/`, `builder/dist/`, `beta/site/builder/`
5. **테스트**
   - vitest: 앱 상태 저장소(노드 추가·연결·Undo·자동 저장 왕복)와 라이브러리 목록 필터
   - 루트 `npm test`에는 넣지 않는다. 루트는 의존성 없이 돈다
   - 브라우저 시험(Playwright)은 B-05에서 상호작용과 함께 넣는다. 이번에는 빌드한 앱을 열어 수동으로 확인한 결과를 기록한다
6. **문서**
   - `builder/README.md`: 실행·빌드·테스트 명령, 구조
   - `builder/CHANGELOG.md`: v0.1.0
   - 루트 README, 이 작업 파일, `Work/빌더/README.md`

### 하지 않을 것

- 근접 연결·범위 선택·가운데 버튼 이동·이슈 패널 (B-05)
- 평행선 일괄 연결, 오토 레이아웃·교차 점프·평행선 간격 이식, 주석 편집 모달, PDF·SVG 내보내기, 다크 모드 (P5)
- Portal 메뉴의 Builder 링크 교체. 새 Builder가 구 Builder 수준이 되는 P5 뒤에 바꾼다(통합 기획 §0 D7)
- 팀 저장·공유 링크 (P8)

### 지킬 결정

- 1.1 호환 JSON(엔진이 보장한다)
- 노드 1개 = 1대, 단자 1개 = 연결 1개
- 전원선은 긋지 않는다
- 저장은 로컬만(D6)
- 실제 구성도 파일을 커밋하지 않는다
- 루트 의존성 0개

## 검증 방법

```powershell
cd builder; npm ci; npm run typecheck; npm test; npm run build; npm run preview
node builder/cli/validate.mjs <내보낸 파일>
```

이 밖에 공통 검증을 돌린다: LF 복제본 전체 테스트, `verify-pages`, 검색 인덱스 `--check`, `git diff --check`. 병합 뒤에는 공개 주소를 열어 확인한다.

## 결정이 필요한 사항

| ID | 항목 | 기본값 | 이유 |
|---|---|---|---|
| G-a | Builder 빌드 실패가 Pages 배포를 막는 문제 | `builder-ci.yml`로 PR에서 먼저 잡는다. 저장소 보호 규칙(필수 검사 지정)은 바꾸지 않는다 | 보호 설정 변경은 사용자 권한이다(AGENTS.md) |
| G-b | Portal 메뉴에 새 Builder 링크를 언제 넣을지 | P5 뒤에 기존 링크와 바꾼다. 그 전까지 새 Builder는 주소로만 연다 | 구 Builder보다 기능이 적은 상태로 사용자를 옮기지 않는다 |
| G-c | 화면 스타일 | Portal의 밝은 스타일. 다크 모드는 P5 | Portal과 한 서비스로 보이게 한다 |

## 작업 방식

| 일 | 맡기는 곳 | 근거 |
|---|---|---|
| 앱 골격·화면·상태 저장소 | 직접 | 엔진과 형식을 알고 있다. 결과는 CLI 검증·vitest·수동 확인이 잡는다 |
| 워크플로 | 직접 | 기존 Pages 단계와의 순서가 중요하다 |
